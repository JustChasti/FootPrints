# Footprints

Небольшой сервис, который по расписанию делает случайные коммиты в репозитории Bitbucket, выбранные инженером

## Как это работает

1. Инженер регистрируется и передаёт свой персональный токен Bitbucket
2. Сервис выдаёт ему JWT и кладёт его в cookies, дальше инженер ходит с этим токеном
3. Инженер создаёт таски. В таске указываются ссылка на репозиторий Bitbucket, ветка, имя коммита (как правило название задачи в Jira), дни недели запуска (по умолчанию понедельник-пятница), рабочее окно (по умолчанию 9:00-18:00), число коммитов в день (по умолчанию 1) и признак активности, чтобы таску можно было выключить. Репозиториев может быть несколько, под каждый своя таска
4. Сервис сам выбирает случайные моменты внутри окна по числу коммитов и делает коммиты в нужное время
5. Инженер смотрит статус своих тасок: сколько раз каждая запускалась всего и когда был последний запуск

## Что планируется

- Язык: Go
- Фреймворк: Fiber
- База: Postgres, доступ через ORM GORM, таблицы создаются при старте из структур
- Интерфейс: Swagger, фронта на первом этапе нет
- Содержимое коммитов: каждый коммит добавляет один новый файл `autocommit/<дата>/<хэш>.txt` с 32-64 строками случайных хэшей

## Структура

```
main.go        конфиг, подключение к базе, запуск ядра и сервера, остановка по сигналу
config/        настройки: task_settings, auth_settings, pg_settings, api_settings, core_settings, bitbucket_settings
core/          ядро: фоновая горутина планирует коммиты на день и запускает их, клиент REST API Bitbucket Server, генератор файла коммита
router/        маршруты /api/v1 и Swagger UI
services/      обработчики Fiber по сервисам: auth, tasks, users (apierr переводит ошибки доменов в коды ответов)
models/db/     сущности базы, они же тела запросов для тасок (теги json и gorm), записи планировщика planned_commits, подключение к базе с ретраями
models/api/    тела запросов и ответов, которых нет в db (регистрация, вход, пользователь, ошибка)
domains/       бизнес-логика: пароли и JWT, шифрование токена Bitbucket, работа с таблицами
docs/          swagger.json, генерируется
Dockerfile     сборка образа, swagger.json генерируется внутри
```

### Настройки

Значения читаются из `.env` (шаблон в `.env.example`) или из переменных окружения. Обязательные: `PG_PASSWORD`, `AUTH_JWT_SECRET`, `AUTH_ENC_KEY` (32 байта в hex, например `openssl rand -hex 32`). Остальное имеет значения по умолчанию в `config/config.go`: `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_DB`, `PG_CONNECT_ATTEMPTS` (10), `PG_CONNECT_DELAY` (3s), `API_HOST` (0.0.0.0), `API_PORT` (8080), `CORE_TICK_INTERVAL` (10m), `BITBUCKET_API_VERSION` (1.0). Значения по умолчанию для тасок (дни, окно, число коммитов, активность) и TTL токена (неделя) лежат там же

`CORE_TICK_INTERVAL` это период опроса ядра и одновременно шаг сетки, на которую попадают времена коммитов (формат `10m`, `30s`). Для проверок его можно ускорить до секунд. Локально на Windows `API_HOST=127.0.0.1` убирает запрос брандмауэра при старте, в контейнере остаётся 0.0.0.0

При старте приложение ждёт базу: пробует подключиться `PG_CONNECT_ATTEMPTS` раз с паузой `PG_CONNECT_DELAY` и только потом завершается с ошибкой

### Запуск

1. Postgres в Docker внутри WSL: `wsl -e docker run -d --name footprints-pg --restart unless-stopped -e POSTGRES_USER=footprints -e POSTGRES_PASSWORD=<пароль> -e POSTGRES_DB=footprints -p 5432:5432 postgres:17`
2. Скопировать `.env.example` в `.env` и заполнить
3. `go generate ./...`, обязательный шаг (см. ниже)
4. `go run .`, Swagger UI открывается на `http://localhost:8080/swagger`

`docs/swagger.json` генерируется по swag-аннотациям и лежит в `.gitignore`, в репозиторий его не кладём. Бинарник вшивает файл через `go:embed`, поэтому без него `go build` падает с ошибкой `no matching files found`. Генерацию нужно запускать после клонирования и после любого изменения аннотаций или моделей. Для неё нужна утилита `swag`: `go install github.com/swaggo/swag/cmd/swag@v1.16.4`

Если WSL закрывает машину по простою, контейнер останавливается. Лечится параметром `vmIdleTimeout=-1` в `%UserProfile%\.wslconfig` (секция `[wsl2]`)

### Docker

Образ собирается в два этапа (`Dockerfile`). В сборочном `go generate` запускает `swag` и создаёт `docs/swagger.json`, поэтому на машине сборки не нужны ни `swag`, ни сгенерированный файл. Итоговый образ это один статический бинарник на Alpine, процесс идёт под uid 10001, пишет только в базу и в сеть, корневая файловая система может быть только на чтение. `.env` в образ не попадает (`.dockerignore`), настройки приходят переменными окружения

```
docker build -t footprints .
docker run -d --name footprints -p 8080:8080 \
  -e PG_HOST=<хост базы> -e PG_PASSWORD=... -e AUTH_JWT_SECRET=... -e AUTH_ENC_KEY=... \
  footprints
```

Если база запущена в Docker на той же машине, оба контейнера кладут в одну сеть (`docker network create`, `--network`), а в `PG_HOST` указывают имя контейнера базы

В закрытом контуре модули Go берутся через `--build-arg GOPROXY=<внутренний прокси>`, а образы в `FROM` (`golang:1.26.8-alpine`, `alpine:3.21`) меняются на адреса внутреннего реестра. Окна тасок считаются во времени сервера, в контейнере это UTC, пояс задаётся переменной `TZ` (например `-e TZ=Europe/Moscow`), база часовых поясов вшита в бинарник тегом сборки `timetzdata`

Swagger UI (`/swagger`) подтягивает скрипты и стили с `unpkg.com`, без доступа в интернет страница остаётся пустой. Сама спецификация отдаётся по `/swagger.json` и от интернета не зависит

### API

Префикс `/api/v1`. Токен JWT выдаётся при регистрации и входе и лежит в cookie `token`

| Метод | Путь | Доступ |
|---|---|---|
| POST | `/auth/register` | открыт |
| POST | `/auth/login` | открыт |
| POST, GET | `/tasks` | JWT |
| GET, PUT, DELETE | `/tasks/{id}` | JWT |
| GET | `/users` | JWT |
| GET | `/users/{id}` | JWT |

`PUT /tasks/{id}` меняет только присланные поля, остальные остаются прежними. `/users` отдаёт логин и число тасок пользователя

В ответах по таскам есть поля только для чтения: `done_commits` и `failed_commits` (удачные и неудачные коммиты за всё сохранённое время, просроченные записи считаются неудачными) и `last_run_at` (время последнего запуска пуша, `null` если запусков не было)

### Как работает авторизация

Проверка JWT вынесена в middleware `Require` и вешается на группу маршрутов одной строкой:

```go
tasksGroup := v1.Group("/tasks", authSvc.Require)
```

Fiber ставит `Require` перед каждым обработчиком группы. Он читает cookie `token`, проверяет подпись и срок, и при ошибке отвечает 401, а обработчик не запускается. Если токен верный, `Require` кладёт id пользователя в `c.Locals` (хранилище на время одного запроса) и вызывает `c.Next()`. Обработчик достаёт id функцией `auth.UserID(c)`, никаких проверок внутри него нет. Id берётся только из подписанного токена, подменить его запросом нельзя. Подробности и причины выбора: `reference/0006-auth-require-middleware-and-locals.md`

### Как работает ядро

Фоновая горутина из `core/` просыпается на точках сетки (при шаге 10 минут это 10:00, 10:10, 10:20) и делает два шага

1. Планирует день. Для каждой активной таски, у которой нет записей на сегодня, выбирает `commits_per_day` случайных разных слотов внутри рабочего окна (точки сетки не раньше текущего опроса, конец окна не входит) и записывает их в таблицу `planned_commits`. Если сегодня не день запуска таски или окно закрыто, ничего не пишется. Отдельного сброса нет: вчерашние записи сами перестают считаться сегодняшними
2. Запускает записи, чьё время пришло (`planned_at <= now`, таска активна). Успех даёт статус `done` и id коммита в `commit_id`, ошибка пуша даёт `failed` с текстом в `error`, повтора в этот день нет. Просроченная запись (из прошлых суток или после `end_time`) получает `failed` с причиной, пуш по ней не делается

Пуш это настоящий коммит в Bitbucket (раздел ниже). Окно и дни недели считаются во времени сервера. Правка расписания таски посреди дня действует со следующего дня, `active` действует сразу. Сервис рассчитан на один экземпляр. По Ctrl+C или SIGTERM текущий пуш доделывается, новые не начинаются, процесс выходит. Подробности и причины выбора: `reference/0007-daemon-planned-commits-and-grid.md`

### Как делается коммит

Один коммит это один запрос к REST API Bitbucket Server, клона репозитория нет (решение `reference/0001-git-via-bitbucket-rest-api.md`):

```
PUT <схема>://<хост>/rest/api/<версия>/projects/<KEY>/repos/<slug>/browse/<путь файла>
Authorization: Bearer <токен инженера>
```

Адрес в `repo_url` инженер берёт из браузера, сервис сам превращает его в адрес API: `https://bitbucket.example.com/projects/PROJ/repos/repo-name/browse` даёт `https://bitbucket.example.com/rest/api/1.0/projects/PROJ/repos/repo-name`. Версия API берётся из `BITBUCKET_API_VERSION`. Другие виды адреса (адрес клона `/scm/...`, личные репозитории `/users/...`, Bitbucket Cloud) пока не поддерживаются: запись получает `failed` с текстом `unsupported repo_url`. Валидации адреса в API нет, ошибка видна только при коммите

Каждый коммит добавляет один новый файл `autocommit/<yyyy-mm-dd>/<имя>.txt`: 32-64 строки, в каждой случайный sha256 в hex. Имя это первые 12 символов sha256 содержимого. Сообщение коммита это `commit_name` таски, ветка берётся из таски и должна уже существовать. Автором Bitbucket назначает владельца токена. Id созданного коммита сохраняется в `planned_commits.commit_id`. Запрос ограничен таймаутом 30 секунд, повторов нет

Шифрование относится к токену Bitbucket, который инженер вводит при регистрации, и работает только для хранения в базе: в `users.bitbucket_token` лежит шифротекст AES-GCM, ключ `AUTH_ENC_KEY`. Перед запросом ядро расшифровывает токен, и он живёт в памяти до конца этого запроса. Сами запросы к Bitbucket сервис не шифрует, на проде их защищает HTTPS. После смены `AUTH_ENC_KEY` сохранённые токены перестают расшифровываться, пуши по ним получают `failed`

## Что поправить позже

- Заголовок вкладки Swagger UI сейчас «Fiber API documentation» (значение по умолчанию библиотеки). Меняется полем `Title` в `swaggerui.Config`, файл `router/router.go`
- Очистка записей `planned_commits` старше двух месяцев, иначе они копятся. После неё `done_commits`, `failed_commits` и `last_run_at` будут показывать только последние два месяца
- Cookie с JWT выдаётся без флага `Secure`, это нужно только для работы по `http://localhost`. Когда сервис поедет за HTTPS, добавить `Secure: true` в `fiber.Cookie`, файл `services/auth/auth.go`
- Swagger UI зависит от `unpkg.com`. В `swaggerui.Config` есть поля `SwaggerURL`, `SwaggerPresetURL`, `SwaggerStylesURL`, `Favicon32` и `Favicon16`: ими можно указать внутреннее зеркало или раздавать файлы самим из бинарника, файл `router/router.go`
- Bitbucket Cloud не поддерживается. Его API другой (`POST /2.0/repositories/{workspace}/{repo}/src`), а личный API-токен Atlassian (`ATATT3...`) принимается только как Basic `email:токен`, Bearer даёт 401
- Валидация `repo_url` в API: сейчас проходит любой http(s) адрес, а нерабочий виден только в `error` записи после попытки коммита

## Статус

Ранняя стадия: работают регистрация, вход, CRUD тасок и чтение пользователей (девять методов API, Swagger), данные лежат в Postgres, фоновое ядро планирует коммиты на день и запускает их в нужное время. Коммиты делаются через REST API Bitbucket Server и проверены на локальной подделке сервера. Живой проверки на настоящем Bitbucket ещё не было. Работа идёт по спекам из каталога `specs/`
