# Footprints

Небольшой сервис, который по расписанию делает случайные коммиты в репозитории Bitbucket, выбранные инженером

## Как это работает

1. Инженер регистрируется и передаёт свой персональный токен Bitbucket
2. Сервис выдаёт ему JWT и кладёт его в cookies, дальше инженер ходит с этим токеном
3. Инженер создаёт таски. В таске указываются ссылка на репозиторий Bitbucket, ветка, имя коммита (как правило название задачи в Jira), дни недели запуска (по умолчанию понедельник-пятница), рабочее окно (по умолчанию 9:00-18:00), число коммитов в день (по умолчанию 1) и признак активности, чтобы таску можно было выключить. Репозиториев может быть несколько, под каждый своя таска
4. Сервис сам выбирает случайные моменты внутри окна по числу коммитов и делает коммиты в нужное время
5. Инженер смотрит статус своих тасок: сколько раз каждая запускалась всего и когда был последний запуск

## Что планируется

- Язык: Go
- Фреймворк: Fiber
- База: Postgres, доступ через ORM GORM, таблицы создаются при старте из структур
- Интерфейс: Swagger, фронта на первом этапе нет
- Содержимое коммитов: сервис создаёт в репозитории новые файлы или наполняет существующие, чем именно, пока не определено

## Структура

```
main.go        конфиг, подключение к базе, сборка и запуск сервера
config/        настройки: task_settings, auth_settings, pg_settings, api_settings
router/        маршруты /api/v1 и Swagger UI
services/      обработчики Fiber по сервисам: auth, tasks, users (apierr переводит ошибки доменов в коды ответов)
models/db/     сущности базы, они же тела запросов для тасок (теги json и gorm), подключение к базе с ретраями
models/api/    тела запросов и ответов, которых нет в db (регистрация, вход, пользователь, ошибка)
domains/       бизнес-логика: пароли и JWT, шифрование токена Bitbucket, работа с таблицами
docs/          swagger.json, генерируется
```

### Настройки

Значения читаются из `.env` (шаблон в `.env.example`) или из переменных окружения. Обязательные: `PG_PASSWORD`, `AUTH_JWT_SECRET`, `AUTH_ENC_KEY` (32 байта в hex, например `openssl rand -hex 32`). Остальное имеет значения по умолчанию в `config/config.go`: `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_DB`, `PG_CONNECT_ATTEMPTS` (10), `PG_CONNECT_DELAY` (3s), `API_HOST` (0.0.0.0), `API_PORT` (8080). Значения по умолчанию для тасок (дни, окно, число коммитов, активность) и TTL токена (неделя) лежат там же

При старте приложение ждёт базу: пробует подключиться `PG_CONNECT_ATTEMPTS` раз с паузой `PG_CONNECT_DELAY` и только потом завершается с ошибкой

### Запуск

1. Postgres в Docker внутри WSL: `wsl -e docker run -d --name footprints-pg --restart unless-stopped -e POSTGRES_USER=footprints -e POSTGRES_PASSWORD=<пароль> -e POSTGRES_DB=footprints -p 5432:5432 postgres:17`
2. Скопировать `.env.example` в `.env` и заполнить
3. `go generate ./...`, обязательный шаг (см. ниже)
4. `go run .`, Swagger UI открывается на `http://localhost:8080/swagger`

`docs/swagger.json` генерируется по swag-аннотациям и лежит в `.gitignore`, в репозиторий его не кладём. Бинарник вшивает файл через `go:embed`, поэтому без него `go build` падает с ошибкой `no matching files found`. Генерацию нужно запускать после клонирования и после любого изменения аннотаций или моделей. Для неё нужна утилита `swag`: `go install github.com/swaggo/swag/cmd/swag@v1.16.4`

Если WSL закрывает машину по простою, контейнер останавливается. Лечится параметром `vmIdleTimeout=-1` в `%UserProfile%\.wslconfig` (секция `[wsl2]`)

### API

Префикс `/api/v1`. Токен JWT выдаётся при регистрации и входе и лежит в cookie `token`

| Метод | Путь | Доступ |
|---|---|---|
| POST | `/auth/register` | открыт |
| POST | `/auth/login` | открыт |
| POST, GET | `/tasks` | JWT |
| GET, PUT, DELETE | `/tasks/{id}` | JWT |
| GET | `/users` | JWT |
| GET | `/users/{id}` | JWT |

`PUT /tasks/{id}` меняет только присланные поля, остальные остаются прежними. `/users` отдаёт логин и число тасок пользователя

### Как работает авторизация

Проверка JWT вынесена в middleware `Require` и вешается на группу маршрутов одной строкой:

```go
tasksGroup := v1.Group("/tasks", authSvc.Require)
```

Fiber ставит `Require` перед каждым обработчиком группы. Он читает cookie `token`, проверяет подпись и срок, и при ошибке отвечает 401, а обработчик не запускается. Если токен верный, `Require` кладёт id пользователя в `c.Locals` (хранилище на время одного запроса) и вызывает `c.Next()`. Обработчик достаёт id функцией `auth.UserID(c)`, никаких проверок внутри него нет. Id берётся только из подписанного токена, подменить его запросом нельзя. Подробности и причины выбора: `reference/0006-auth-require-middleware-and-locals.md`

## Что поправить позже

- Заголовок вкладки Swagger UI сейчас «Fiber API documentation» (значение по умолчанию библиотеки). Меняется полем `Title` в `swaggerui.Config`, файл `router/router.go`
- Cookie с JWT выдаётся без флага `Secure`, это нужно только для работы по `http://localhost`. Когда сервис поедет за HTTPS, добавить `Secure: true` в `fiber.Cookie`, файл `services/auth/auth.go`
