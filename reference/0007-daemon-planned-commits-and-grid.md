# reference 0007: Расписание строками planned_commits, сетка по периоду опроса

Статус: принято (уточняет `0004`: схема таблицы `planned_commits` и момент построения плана)

Дата: 2026-10-15

## Контекст

Спека 003 вводит фоновую горутину, которая запускает функцию пуша в нужное время. Первая идея в спеке: хранить в таске статус и ближайшее время запуска, раз в сутки в заданный час статусы обнулять, а опрос раз в период выполнял бы таски, которым пришло время. В `0004` для тех же целей описана таблица `planned_commits`. После обсуждения (счётчик неудач, статистика запусков, круглые времена) таблица оказалась проще, чем состояние в таске

## Решение

Расписание хранится строками в таблице `planned_commits`, по одной записи на коммит:
- поля: `task_id`, `planned_at` (плановое время слота), `status`, `executed_at` (когда пуш запускался), `error`
- статусы: `planned` (ждёт времени), `done` (пуш прошёл), `failed` (коммита нет: пуш вернул ошибку или запись просрочена)
- уникальный индекс `(task_id, planned_at)`, каскадное удаление вместе с таской

План дня строится на первом опросе дня для каждой активной таски, у которой ещё нет записей на сегодня. Отдельного часа и отдельного сброса нет: вчерашние записи перестают считаться сегодняшними сами. Таска, созданная или включённая посреди дня, планируется на остаток окна на ближайшем опросе

Времена выбираются на сетке. Шаг сетки равен периоду опроса `CORE_TICK_INTERVAL` (по умолчанию 10 минут), точки привязаны к часам (`10:00`, `10:10`, `10:20`). Слоты таски это точки сетки внутри окна `[start_time, end_time)` не раньше текущего опроса. Из них случайно выбираются `min(commits_per_day, число слотов)` разных. Опросы выравниваются по сетке, поэтому запись на `10:20` выполняется на опросе в `10:20`

Запуск: опрос берёт записи `planned` с `planned_at <= now` у активных тасок и вызывает `push`. Успех даёт `done`, ошибка даёт `failed` с текстом в `error`, повтора в этот день нет, потому что ошибка пуша считается ошибкой системы. Просроченная запись (из прошлых суток или после `end_time` таски) получает `failed` с причиной, пуш по ней не делается. Отдельного статуса для просроченных нет, причина различается текстом в `error`

Горутина останавливается по сигналу через `context`: текущий пуш доделывается, новые не начинаются, `main` ждёт завершения

Счётчики `done_commits`, `failed_commits` и дата `last_run_at` в ответах по таскам считаются при чтении по записям таски (`Preload` и подсчёт в Go), в таблице тасок их нет

## Рассмотренные варианты

- Состояние в таске (`commits_today`, `next_run_at`, `planned_day`): проще, пока нет счётчика неудач и статистики. С ними нужны отдельный счётчик, защита от затирания состояния при `PUT` (`Omit` в `Save`) и формула выбора времени, иначе коммиты сбиваются к концу окна. Отвергнуто
- Утренний час для обнуления из спеки: рестарт после этого часа теряет день, окно раньше этого часа ломается, таска посреди дня ждёт до завтра. Заменено проверкой "спланирован ли сегодня" на каждом опросе
- Статус `missed` для просроченных записей: функционально отличается от `failed` только причиной, которую несёт текст в `error`. Отвергнуто

## Последствия

- Расписание переживает рестарт, состояние хранится в базе
- Сервис рассчитан на один экземпляр (`replicas: 1`, см. `0003`), блокировок выбора записей нет
- Окно и дни недели считаются во времени сервера (в контейнере обычно UTC)
- Правка расписания таски посреди дня действует со следующего дня, `active` действует сразу
- Записи накапливаются, пока нет очистки. Счётчики считаются по всем сохранённым записям таски

## Открытые вопросы

- Очистка записей старше двух месяцев (запланирована следующим шагом, после неё счётчики и `last_run_at` будут отражать только последние два месяца)
- `commit_id` в записи, появится вместе с настоящим пушем в Bitbucket
- Окно через полночь и часовой пояс таски (остаются открытыми из `0004`)
