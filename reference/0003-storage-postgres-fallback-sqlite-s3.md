# reference 0003: Хранилище состояния. Внешний Postgres, запасные варианты SQLite + Litestream и SlateDB

Статус: принято (основной вариант Postgres, запасные варианты А: SQLite + Litestream и Б: SlateDB, выбор между ними после проверок, см. ниже)

Дата: 2026-10-09

## Контекст

Сервис автоматизации коммитов хранит пользователей (id, зашифрованный токен Bitbucket, репозиторий, ветка, story, число коммитов в день, cron), план коммитов на день и историю выполненных коммитов. План нужно хранить, чтобы после рестарта пода не потерять уже выбранные случайные времена и знать, что сделано. Из истории считается статистика по инженеру

Сервис разворачивается на платформе Сбера в dev-контуре, в пром не едет. Ограничения платформы:
- Постоянные тома запрещены (подтверждено ответом от команды платформы). В чартах и values нет ни одного `persistentVolumeClaim`, `StatefulSet`, `storageClass`, `hostPath`
- Из томов доступны `emptyDir` (на диске ноды), `configMap` и тома Vault-инжектора. `app.mounts[]` умеет только `emptyDir`
- Корневая файловая система пода read-only, процесс под uid 10001, писать можно в `/tmp`
- Состояние приложений живёт во внешних БД, которые подключаются через `tcp_servers`

Из этого следует, что всё, что должно пережить рестарт пода, лежит либо во внешней БД, либо в S3

## Решение

Основной вариант: внешний PostgreSQL

Запасные варианты, если в Postgres откажут:
- А: SQLite в файле на `emptyDir` с непрерывной репликацией в S3 через Litestream
- Б: SlateDB, встраиваемый KV, который хранит данные прямо в S3

Выбор между А и Б делается по двум проверкам (раздел «Выбор между А и Б»). Оба варианта работают внутри процесса приложения, отдельного сервера и деплоя не требуют

Слой хранения оформляется как интерфейс операций сервиса: создать пользователя, запланировать коммиты, взять ближайший к выполнению, отметить выполненным, статистика по пользователю. Во всех вариантах сервис работает в одной реплике (`replicas: 1`). Для Postgres и варианта А реализация общая на `database/sql`, запросы пишутся в общем подмножестве SQL (без `FOR UPDATE SKIP LOCKED` и других расширений Postgres), чтобы переключение между ними не требовало переписывать слой хранения. Для варианта Б нужна отдельная реализация на ключах. Выбор задачи воркером в SQL-реализации делается так:

```sql
UPDATE planned_commits SET status = 'running'
WHERE id = (SELECT id FROM planned_commits WHERE status = 'new' AND run_at <= :now ORDER BY run_at LIMIT 1)
RETURNING id, user_id
```

Он работает и в Postgres, и в SQLite 3.35 и новее

## Схема данных

- `users`: id, токен (шифруется AES-GCM, ключ из env, лежит в Vault), репозиторий, ветка, story, число коммитов в день, cron
- `planned_commits`: id, user_id, run_at, status, done_at, commit_id, error
- Статистика считается агрегатами по `planned_commits`

## Основной вариант: внешний Postgres

Подключение штатными средствами платформы:
- `app.postgre[]` в values: логин и пароль приходят из Vault (`static-creds/<database>_<username>`) файлом в `/vault/secrets`
- `tcp_servers` с `protocol: postgres` для хоста БД (egress с StartTLS)
- Драйвер `pgx`

Экономия: новый инстанс заказывать не обязательно. В соседних неймспейсах уже есть `techdb-pg*`, и `app.postgre[]` умеет вторую БД через `db_name`. Попросить стоит отдельную базу или схему на существующем dev-инстансе (уверенность, что так разрешат, около 70%)

Плюсы:
- Бэкапы, доступность и надёжность остаются на стороне платформы
- Для Postgres в чартах есть готовая обвязка, ничего дописывать не нужно
- Данные реляционные, статистика это обычные `GROUP BY`

Минусы:
- Нужно получить БД и доступы, срок согласования неизвестен
- Требуются записи в egress и в Vault

## Запасной вариант А: SQLite + Litestream + S3

Схема работы:
- Файл БД `/tmp/app.db` лежит на `emptyDir`
- Litestream в фоне отправляет WAL в S3, интервал по умолчанию около секунды
- Entrypoint контейнера ждёт появления файла с кредами S3 в `/vault/secrets`, восстанавливает БД из S3 и запускает приложение как дочерний процесс Litestream

Набросок entrypoint (имена файлов и ключи конфига сверить с версией Litestream):

```sh
#!/bin/sh
while [ ! -f /vault/secrets/s3 ]; do sleep 1; done
export LITESTREAM_ACCESS_KEY_ID="$(cat /vault/secrets/s3-key)"
export LITESTREAM_SECRET_ACCESS_KEY="$(cat /vault/secrets/s3-secret)"
litestream restore -if-db-not-exists -if-replica-exists -config /etc/litestream.yml /tmp/app.db
exec litestream replicate -exec /app/server -config /etc/litestream.yml
```

```yaml
dbs:
  - path: /tmp/app.db
    replicas:
      - type: s3
        bucket: <bucket>
        path: footprints/app.db
        endpoint: https://<s3-host>
        force-path-style: true
```

Требования и ограничения:
- Один писатель: `replicas: 1` и `app.update_strategy: Recreate`. При RollingUpdate старый и новый поды одновременно пишут в одну реплику в S3 и портят её
- Бинарник `litestream` в образе приложения, драйвер SQLite на чистом Go (`modernc.org/sqlite`), без CGO
- Восстановление делается в entrypoint основного контейнера. В init-контейнере оно, скорее всего, упадёт: init-контейнеры стартуют до `istio-proxy`, а `holdApplicationUntilProxyStarts` ждёт прокси только перед основными контейнерами (уверенность около 75%, зависит от версии Istio в «Synapse» и наличия native sidecars)
- Креды S3 приходят из Vault файлами асинхронно, поэтому entrypoint ждёт их перед `restore`
- Запись `http_servers` или `tcp_servers` на хост S3 в egress. S3-хосты (`bennu-edz`, `nun-edz`) в материалах упомянуты, детали подключения неизвестны
- Совместимость Litestream с S3 Сбера (кастомный endpoint, path-style) не проверена, уверенность около 75%

Плюсы:
- Нет отдельного сервера и отдельного деплоя
- Не нужно согласовывать БД, нужен только бакет S3
- При жёстком падении теряется около секунды записей, для расписания коммитов это допустимо

Минусы:
- За сохранность данных отвечает сервис, а не платформа
- Один писатель, горизонтально не масштабируется
- Старт пода дольше на время восстановления из S3

## Запасной вариант Б: SlateDB (встраиваемый KV, S3 как основное хранилище)

SlateDB это встраиваемая библиотека на Rust: LSM-дерево, которое пишет WAL и SSTable прямо в объектное хранилище. Источником истины служит S3, локальный файл БД не нужен. Отдельного сервера, контейнера и деплоя нет, библиотека работает внутри процесса приложения. Подключение: `go get slatedb.io/slatedb-go` (по документации нужен Go 1.25 и новее). Интерфейс: `put`, `get`, `delete`, `scan`, пакеты записей и транзакции с уровнями изоляции

Как это устроено:
- Запись: `put` или `WriteBatch` попадает в WAL-буфер и memtable. WAL сбрасывается в S3 как WAL SST по размеру буфера или по `flush_interval`. Замороженная memtable пишется в S3 как L0 SSTable, компактор сливает L0 в sorted runs
- По умолчанию `put` возвращается после того, как WAL оказался в S3 (`await_durable`), то есть подтверждение коммита стоит одного PUT. При `await_durable = false` ответ быстрее, но не дошедшие до S3 записи теряются при падении
- Манифест лежит в `manifest/<id>.manifest`, каждый файл это полный снимок состояния, обновление идёт через compare-and-swap на следующий id
- Fencing писателя: при старте `writer_epoch` в манифесте увеличивается, а старый писатель, увидевший больший epoch, останавливается. Зомби-под данные не портит
- Компактор может работать в процессе писателя или отдельно, нам нужен один процесс с встроенным компактором
- Два слоя кэша: блочный и object-store, второй можно разместить на `/tmp`

Набросок схемы ключей (API Go-привязки не проверялся):

```
u/<user_id>                           → JSON пользователя
p/<run_at_unix_ms, 8 байт big-endian>/<id> → запланированный коммит, ключи упорядочены по времени
c/<user_id>/<yyyy-mm-dd>/<id>          → выполненный коммит (commit_id, status, done_at)
```

- Выбор задачи: scan префикса `p/` до текущего времени
- Отметка выполнения: транзакция, которая удаляет `p/...` и пишет `c/...`
- Статистика: scan префикса `c/<user_id>/` и агрегаты в коде на Go

Требования и ограничения:
- Один писатель: `replicas: 1`. `app.update_strategy: Recreate` остаётся желательным, но при перекрытии подов fencing останавливает старого писателя и данные остаются целыми (у варианта А такой защиты нет)
- Шага `restore` и бинарника Litestream нет, БД открывается по пути в бакете. Креды S3 из Vault приходят файлами асинхронно, поэтому перед открытием БД приложение ждёт файл с кредами
- Go-привязка использует нативную библиотеку (uniffi), вероятно с CGO. Нужно проверить сборку в базовом образе платформы (glibc или musl, возможна ли сборка с CGO), уверенность в том, что это пройдёт без боли, около 70%
- Egress на хост S3 так же, как в варианте А
- Условные записи: S3 Сбера должен поддерживать compare-and-swap (If-None-Match, If-Match). По RFC-0001 SlateDB, если их нет, для манифеста нужно дополнительное транзакционное хранилище (в RFC приведён пример с DynamoDB). RFC мог отстать от кода, актуальные требования сверить с текущей документацией
- SQL нет: выборки и статистика пишутся вручную через scan по префиксам, модель ключей фиксируется заранее
- Проект молодой, версия и стабильность на момент разработки не проверены

Плюсы:
- Ничего не нужно поднимать, БД это бакет S3
- Нет шага восстановления при старте и нет Litestream в образе
- Fencing писателя встроен
- Чекпойнты манифеста фиксируют состояние БД без копирования данных. Защита от случайного удаления (versioning и object lock в S3) всё равно нужна

Минусы:
- KV без SQL, нужна отдельная реализация слоя хранения
- Молодая зависимость и нативная библиотека в образе
- Риск, что S3 Сбера не поддерживает условные записи
- За сохранность данных отвечает сервис, а не платформа

## Выбор между А и Б

|  | А: SQLite + Litestream | Б: SlateDB |
|---|---|---|
| Модель данных | SQL | KV |
| Источник истины | локальный файл, S3 хранит копию | S3 |
| Восстановление при старте | `restore` из S3, время растёт с размером БД | не нужно |
| Защита от двух писателей | только `Recreate` | fencing по epoch |
| В образе | бинарник `litestream`, SQLite на чистом Go | нативная библиотека SlateDB, вероятно CGO |
| Зрелость | Litestream давно используется | молодой проект |
| Главный риск | совместимость с S3 Сбера | условные записи на S3 Сбера и сборка нативной библиотеки |

Две проверки, которые определяют выбор:
1. Условные записи на S3 Сбера: два PUT одного ключа с заголовком `If-None-Match: *`, второй должен вернуть 412. Если не вернул, вариант Б отпадает
2. Сборка Go-привязки SlateDB в образ платформы (хватает ли CGO и совместимости libc)

Если обе проверки проходят, берётся Б. Если хотя бы одна нет, берётся А

## Отвергнутые варианты

- Файл (SQLite, bbolt, Badger) на `emptyDir` без репликации: данные теряются при каждом рестарте и переезде пода
- Postgres, rqlite или другой сервер БД внутри неймспейса: без постоянного тома данные на `emptyDir` теряются так же. Свой чарт этого не меняет
- Postgres на `emptyDir` с архивом WAL в S3: работает, но это тяжёлый костыль и хуже Litestream
- Redis: статистику считать неудобно, сохранность данных на dev-инстансах неизвестна
- Mongo: в values платформы нет ни одного следа, опереться не на что
- Neon, ClickHouse поверх S3, DuckDB: тяжелее задачи или не подходят для транзакционной записи

## Последствия

- В коде нужен тонкий слой хранения в виде интерфейса операций сервиса. Для Postgres и варианта А это реализация на `database/sql` с запросами в общем подмножестве SQL и одним набором миграций. Если уйдём на вариант Б, потребуется вторая реализация на ключах, поэтому интерфейс не должен протаскивать наружу SQL-специфику
- Токены Bitbucket шифруются в любом варианте, ключ приходит через `app.secrets`
- Во всех вариантах сервис работает в одной реплике

## Открытые вопросы

- Согласуют ли отдельную базу или схему на существующем dev-инстансе Postgres и в какой срок
- Версия Litestream и формат конфига для неё (ключи `type`, `endpoint`, `url` отличаются между версиями)
- Совместимость S3 Сбера с Litestream и порядок получения бакета и кредов
- Версия Istio в «Synapse»: есть ли native sidecars и можно ли восстанавливать БД в init-контейнере
- Поддерживает ли S3 Сбера условные записи (If-None-Match, If-Match) и строгую согласованность, это условие варианта Б
- Собирается ли Go-привязка SlateDB в базовый образ платформы и нужен ли CGO
- Версия и стабильность SlateDB на момент начала разработки, а также то, какой именно API транзакций и scan доступен в Go-привязке
