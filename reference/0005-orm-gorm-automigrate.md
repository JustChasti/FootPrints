# reference 0005: ORM GORM с AutoMigrate вместо SQL-схемы и database/sql

Статус: принято (уточняет раздел «Решение» в `0003`: сам Postgres остаётся основным вариантом, меняется способ работы с ним)

Дата: 2026-10-13

## Контекст

В `0003` слой хранения мыслился как `database/sql` с запросами в общем подмножестве SQL и файлами схемы. Для шага со спекой 002 это неудобно: схему хочется держать в самих структурах Go, а модели таски должны одновременно служить телом запроса API и сущностью базы (без копирования полей из одной структуры в другую)

## Решение

GORM (`gorm.io/gorm` и драйвер `gorm.io/driver/postgres`, внутри него pgx). Структуры несут теги `json` и `gorm`, таблицы создаются при старте через `AutoMigrate`, SQL-файлов со схемой нет

Сравнение:

| | Что даёт | Что не подходит |
|---|---|---|
| GORM | `AutoMigrate` строит таблицы из структур, `json` и `gorm` теги в одной структуре, самая распространённая | `Updates` со структурой пропускает нулевые значения, `AutoMigrate` не удаляет и не переименовывает колонки |
| Bun | ближе к SQL, структуры с тегами, есть пакет миграций | меньше примеров, автосоздания таблиц нет, схему всё равно описывать отдельно |
| ent | типобезопасный, схема на Go | кодогенерация и отдельные сгенерированные типы, это ломает «одну модель на два слоя» |
| sqlc | быстрый, типобезопасный | это и есть SQL-файлы |

## Последствия

- Обновление таски пишется через `Save` целой строки после слияния с текущими значениями, `Updates` со структурой не используется
- Когда схема начнёт меняться на живых данных (переименования, удаления, изменение типов), подключаются версионные миграции, например goose. Заранее их не закладываем
- Интерфейса хранилища нет, домены работают с `*gorm.DB`
- Список дней недели хранится как `jsonb` через сериализатор GORM, отдельные `Scan` и `Value` не нужны
- Запасные варианты из `0003` (SQLite, SlateDB) остаются описанием на случай отказа в Postgres, в коде их нет
