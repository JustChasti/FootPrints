## Контекст

Сервис автоматизации по расписанию создаёт коммиты со случайно сгенерированными файлами от имени инженера: в его репозиторий, в его ветку, с привязкой к story в Jira. Инженер регистрируется в сервисе через Swagger и оставляет id, персональный токен Bitbucket, репозиторий, ветку, story, число коммитов в день и cron

Сервис разворачивается на платформе Сбера в dev-контуре. Постоянные тома там запрещены. В чартах есть только `emptyDir`, корневая файловая система пода доступна только на чтение, процесс идёт под uid 10001, писать можно в `/tmp` (`emptyDir` на диске ноды, в RAM он не лежит, но входит в ephemeral-storage пода). Состояние (пользователи, план коммитов, история) лежит во внешней БД

Этот путь нужен, если REST API Bitbucket из `0001-git-via-bitbucket-rest-api.md` окажется недоступен или запретит запись

## Описание пути

На каждый коммит делается одноразовый неглубокий клон одной ветки, и он удаляется сразу после push:

```bash
git clone --depth 1 --single-branch --branch "$BRANCH" "$URL" /tmp/job-$ID
cd /tmp/job-$ID
# записать сгенерированный файл, например autocommit/<yyyy-mm-dd>/<random>.txt
git add autocommit
git -c user.name="$NAME" -c user.email="$EMAIL" commit -m "$MSG"
git push origin "$BRANCH"
rm -rf /tmp/job-$ID
```

Если сервер принимает partial clone, клон можно сделать ещё легче: `--filter=blob:none --sparse`, затем `git sparse-checkout set autocommit`. Поддержка этих опций вашим Bitbucket не проверена

Токен передаётся через окружение процесса, аргументы командной строки для него не годятся, потому что видны в `/proc`. Нужен git версии 2.31 и новее:

```
GIT_CONFIG_COUNT=1
GIT_CONFIG_KEY_0=http.extraHeader
GIT_CONFIG_VALUE_0="Authorization: Bearer <токен>"
```

## Варианты исполнения

1. Бинарник `git` через `os/exec` (рекомендуется для этого пути). Память расходует отдельный короткоживущий процесс, бинарник нужно добавить в образ
2. Библиотека `go-git` на чистом Go, бинарник не нужен. Клонировать через `PlainClone` на диск в `/tmp`, а `memory.NewStorage()` из примеров не использовать: он держит всё в RAM. На тяжёлых репозиториях go-git разбирает packfile жадно, а partial clone он, насколько известно, не поддерживает (уверенность около 70%). Поддержка push из shallow-клона не проверена

## Плюсы

- Работает с любым git-хостингом, не зависит от версии и расширений Bitbucket
- Поведение такое же, как у человека: те же хуки, те же проверки
- Один коммит может содержать несколько файлов
- Протокол git стандартный, отладка через обычные команды

## Минусы и риски

- Нужен бинарник `git` в образе (вариант 1) или повышенная память на тяжёлой репе (вариант 2)
- Нужны диск в `/tmp` и очистка после каждого коммита, при падении процесса остаются хвосты в `/tmp` до перезапуска пода
- Нужно хранить `name` и `email` автора из профиля инженера, иначе коммит не засчитается как его
- Время коммита зависит от размера репозитория
- Если кто-то двинул ветку между clone и push, push отклоняется. Клон одноразовый, поэтому достаточно повторить весь цикл с начала
- Токен находится в окружении дочернего процесса на время коммита

## Ограничение расхода ресурсов

Главная ручка по памяти и диску это параллелизм. Воркер должен обрабатывать одновременно не больше одного-двух коммитов. Время коммитов в плане случайное, поэтому очередь на 1-2 слота почти не влияет на расписание и режет пик потребления

## Что нужно от окружения

- Запись `http_servers` на хост Bitbucket в values неймспейса, git ходит по HTTPS 443. SSH на порт 7999 потребовал бы `tcp_servers` и ключа на каждого инженера, этот вариант не рассматривается
- Бинарник `git` версии 2.31 и новее в образе (вариант 1)
- Персональный токен инженера с правом записи, `name` и `email` автора
- Ключ шифрования токенов в БД, подаётся через `app.secrets`

## Отвергнуто

S3 как промежуточное хранилище клона или источник файлов. Git создаёт коммит только через push в Bitbucket или через его REST API, из S3 закоммитить нельзя. Хранить клон между запусками в S3 дороже, чем сделать свежий неглубокий клон, а содержимое файлов (случайный текст в пару килобайт) генерируется на лету

## Открытые вопросы

- Разрешён ли в образах платформы бинарник `git`
- Принимает ли сервер `--filter=blob:none` и sparse-checkout
- Размер целевых репозиториев
