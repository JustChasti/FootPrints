# reference 0006: Проверка JWT через middleware Require и передача пользователя через Locals

Статус: принято

Дата: 2026-10-13

## Контекст

Обработчикам тасок и пользователей нужно знать, кто делает запрос: таска принадлежит пользователю, и видеть чужие таски нельзя. JWT приходит в cookie `token` (так записано в README). Хочется, чтобы проверка токена жила в одном месте, а в обработчиках не было ни разбора cookie, ни вызовов проверки

## Решение

Проверка вынесена в middleware `Require` (`services/auth/auth.go`), который вешается на группу маршрутов целиком:

```go
tasksGroup := v1.Group("/tasks", authSvc.Require)
usersGroup := v1.Group("/users", authSvc.Require)
```

Fiber выстраивает для каждого маршрута группы цепочку: сначала `Require`, затем сам обработчик. Ход запроса:

```
Cookie: token=eyJ...
   │
   ▼
Require ── Auth.Parse ── c.Locals(userKey{}, id) ── c.Next() ──┐
   │ (токен плохой)                                            ▼
   ▼                                                    обработчик
ответ 401, цепочка                                      auth.UserID(c)
обрывается                                              возвращает id
```

1. `Require` читает cookie и передаёт её в `Auth.Parse` (`domains/auth.go`)
2. `Parse` проверяет подпись (HS256, секрет `AUTH_JWT_SECRET`), срок `exp` и допустимый алгоритм. Токены на сервере не хранятся, доверие держится на подписи
3. При ошибке `Require` отвечает 401 и не вызывает `c.Next()`, обработчик не запускается
4. При успехе `Require` кладёт id пользователя (claim `sub`) в `c.Locals` и вызывает `c.Next()`
5. Обработчик получает id функцией `auth.UserID(c)` и передаёт его в домен, а домен добавляет `user_id` в условие каждого запроса к таскам

`c.Locals` это хранилище ключ-значение на время одного запроса. Оно создаётся вместе с запросом и исчезает после ответа, запросы друг друга не видят. Через него проверка в одном звене цепочки передаёт результат другому звену, без глобальных переменных и без вложенных вызовов

Ключом служит значение неэкспортируемого типа `type userKey struct{}`, а не строка. Строковый ключ мог бы совпасть с ключом другого middleware, и один затёр бы значение другого. Значение `userKey{}` равно только самому себе: ключи в `Locals` сравниваются как интерфейсы, то есть по типу и значению, а тип `auth.userKey` недоступен за пределами пакета. Ключ можно записать и прочитать только функциями пакета `auth`, и снаружи читают его через единственный доступный метод `UserID`

Id пользователя берётся только из подписанного токена. В теле запроса и в URL его нет, подменить его клиент не может

## Последствия

- Новую защищённую группу маршрутов подключаем так же: `v1.Group("/путь", authSvc.Require)`. Сами обработчики про авторизацию ничего не знают, кроме вызова `auth.UserID(c)`
- Если `Require` забыть, `UserID` вернёт `0`. Пользователей с id 0 нет, поэтому выборки вернут пустой результат, а создание упадёт на внешнем ключе. Чужие данные при этом не раскрываются, но защита всё равно должна стоять на всей группе
- Токен нельзя отозвать до истечения срока (по умолчанию неделя), выхода (logout) пока нет. Это цена того, что сессии не хранятся в базе
- Cookie выдаётся без флага `Secure`, это нужно поправить при переезде на HTTPS (см. раздел «Что поправить позже» в `README.md`)
