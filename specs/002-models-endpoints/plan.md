# План 002: модели, конфиг, эндпоинты

Основание: `spec.md`. Задача: завести модели в Postgres через ORM, конфиг с дефолтами и настройками из `.env`, домены и сервисы под них (auth, tasks, users), роутер, затем прогнать сценарий через живой API. Хождения в API Bitbucket нет, планировщика коммитов нет. Расписание тасок строится по `reference/0004-schedule-work-window-instead-of-cron.md`, основной вариант хранилища Postgres по `reference/0003-storage-postgres-fallback-sqlite-s3.md`. Часть `0003` про `database/sql` и общее подмножество SQL этим планом заменяется на ORM (см. раздел «ORM и схема»)

## Что входит

- `config/config.go` со структурами `TaskSettings`, `AuthSettings`, `PGSettings`, `APISettings`
- Модели на GORM, таблицы `users` и `tasks` создаются при старте из структур, SQL-файлов со схемой нет
- Подключение к базе с ретраями, приложение не падает при недоступной базе в момент старта
- Регистрация и вход: пароль в виде bcrypt-хеша, токен Bitbucket в шифрованном виде, JWT с TTL (по умолчанию неделя) уходит в cookie
- CRUD тасок текущего пользователя, у таски есть ветка
- Сервис users: список пользователей и один пользователь с числом его тасок
- Прогон сценария через API с тестовыми пользователями и тасками

Вне шага: вызовы Bitbucket, планирование и запуск коммитов, поля `runs_total` и `last_run_at` из плана 001 (их считать не из чего, появятся вместе с таблицей запусков)

## Конфиг

`config.Load()` читает `.env` через `godotenv` (если файла нет, берёт переменные окружения как есть, так будет работать в поде) и возвращает `Config{Task, Auth, PG, API}`. Дефолты лежат в самих структурах, без отдельного слоя

| Структура | Поле | Откуда | Значение по умолчанию |
|---|---|---|---|
| `TaskSettings` | `Days` | код | `1,2,3,4,5` |
| | `StartTime` | код | `09:00` |
| | `EndTime` | код | `18:00` |
| | `CommitsPerDay` | код | `1` |
| | `Active` | код | `true` |
| `AuthSettings` | `TokenTTL` | код | 7 суток |
| | `JWTSecret` | `AUTH_JWT_SECRET` | обязателен |
| | `EncKey` | `AUTH_ENC_KEY` | обязателен, 32 байта в hex |
| `PGSettings` | `Host` | `PG_HOST` | `localhost` |
| | `Port` | `PG_PORT` | `5432` |
| | `User` | `PG_USER` | `footprints` |
| | `Password` | `PG_PASSWORD` | обязателен |
| | `DB` | `PG_DB` | `footprints` |
| | `ConnectAttempts` | `PG_CONNECT_ATTEMPTS` | `10` |
| | `ConnectDelay` | `PG_CONNECT_DELAY` | `3s` (формат `time.ParseDuration`) |
| `APISettings` | `Host` | `API_HOST` | `0.0.0.0` |
| | `Port` | `API_PORT` | `8080` |

Хост и порт базы отдельными полями, как просили в спеке, имя базы добавлено, без него DSN не собрать. `PGSettings.DSN()` собирает строку подключения, `APISettings.Addr()` собирает адрес для `app.Listen`. Константа `:8080` из плана 001 уходит

`TaskSettings.Params()` отдаёт свежую заготовку `db.TaskParams` со всеми дефолтами. Срез дней копируется через `slices.Clone`: `encoding/json` при разборе массива дописывает элементы в существующий срез и иначе затёр бы массив с дефолтами в конфиге

## ORM и схема

Схему в SQL-файлах держать не хочется, поэтому берём ORM. Сравнение:

| | Что даёт | Что не подходит |
|---|---|---|
| GORM | `AutoMigrate` строит таблицы из структур, `json` и `gorm` теги живут в одной структуре, самая распространённая, много примеров | «магия»: `Updates` со структурой пропускает нулевые значения, `AutoMigrate` не удаляет и не меняет колонки |
| Bun | ближе к SQL, структуры с тегами, есть пакет миграций | меньше примеров, `AutoMigrate` нет, схему всё равно описывать отдельно |
| ent | типобезопасный, схема на Go | кодогенерация и отдельные сгенерированные типы, что ломает идею «одна модель на два слоя» |
| sqlc | быстрый, типобезопасный | это и есть SQL-файлы |

Выбор: GORM (`gorm.io/gorm` с драйвером `gorm.io/driver/postgres`, внутри он использует pgx). Две оговорки:
- `AutoMigrate` создаёт таблицы и добавляет недостающие колонки, но не переименовывает и не удаляет. Для старта этого достаточно. Когда схема начнёт меняться на живых данных, подключим версионные миграции (например goose), заранее их не закладываем
- `Update` пишем через `Save` полной строки после слияния с текущими значениями, не через `Updates` со структурой, иначе `active: false` потерялся бы как нулевое значение

Решение оформляется заметкой `reference/0005-orm-gorm-automigrate.md` (сравнение выше и оговорки), в `0003` добавляется ссылка на неё. Интерфейса хранилища нет, домены работают с `*gorm.DB` напрямую

## Модели: одна на два слоя

Вопрос из спеки: держать одну модель под БД и под API или конвертировать. Для тасок ответ такой: одна модель, конвертации нет. Поля, которые инженер задаёт сам, собраны в `TaskParams` с тегами `json` и `gorm`. Таска из БД встраивает эти параметры:

```go
type TaskParams struct {
    RepoURL       string   `json:"repo_url"        gorm:"not null"`
    Branch        string   `json:"branch"          gorm:"not null"`
    CommitName    string   `json:"commit_name"     gorm:"not null"`
    Days          Weekdays `json:"days"            gorm:"type:jsonb;serializer:json;not null"`
    StartTime     Clock    `json:"start_time"      gorm:"not null"`
    EndTime       Clock    `json:"end_time"        gorm:"not null"`
    CommitsPerDay int      `json:"commits_per_day" gorm:"not null"`
    Active        bool     `json:"active"          gorm:"not null"`
}

type Task struct {
    ID     int64 `json:"id" gorm:"primaryKey"`
    UserID int64 `json:"-" gorm:"not null;index"`
    User   *User `json:"-" gorm:"constraint:OnDelete:CASCADE"`
    TaskParams
    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at"`
}
```

- Тело `POST` и `PUT` разбирается прямо в `TaskParams`, ответ отдаёт `Task`. Плоский JSON получается сам, потому что `encoding/json` разворачивает встроенную структуру, GORM делает то же для колонок
- Поле `User` нужно только затем, чтобы `AutoMigrate` создал внешний ключ с каскадным удалением, в JSON оно не попадает
- `models/api` для тасок ничего не содержит, в Swagger схемы называются `db.TaskParams` и `db.Task`
- Для пользователя одна модель не годится: в запросе приходит открытый пароль, в базе лежит хеш, и хеш с шифрованным токеном наружу уходить не должны. Здесь два типа (`api.RegisterRequest` и `db.User`), и конвертация между ними делает реальную работу (хеширует и шифрует), так что это не механическое копирование полей
- `db.User`: `ID`, `Login` (уникальный индекс), `PasswordHash`, `BitbucketToken` (байты после AES-GCM), `CreatedAt`, у обоих секретных полей `json:"-"`

### Дни недели

Отдельный тип `Weekdays` на основе `[]int16`, ISO-нумерация: 1 понедельник, 7 воскресенье. В JSON это массив `[1,3,5]`, в Postgres колонка `jsonb` (GORM-сериализатор `json` избавляет от своих `Scan` и `Value`). Дефолт «1-5» это просто значение `[1,2,3,4,5]`. Будущий планировщик найдёт таски на нужный день запросом вида `days @> '[3]'`

Рассмотрено и отброшено:
- строка вида `"1-5,7"`: нужен свой парсер и формат ошибок, а выгоды над массивом нет
- битовая маска: компактно, но в БД и в JSON нечитаемо (`31` вместо `1-5`)
- `smallint[]`: нативнее, но в GORM требует своих `Scan`, `Value` и `GormDBDataType`

### Время суток

Тип `Clock` на основе `string`, формат `HH:MM`, в Postgres колонка `text`. Для окна внутри одних суток строки с нулём в начале сравниваются лексикографически, поэтому `time` в базе и в Go с его конвертациями не нужен. `Validate` приводит `9:00` к `09:00`

### Валидация

Метод `TaskParams.Validate() error` в `models/db`:
- `repo_url` непустой, разбирается как URL со схемой `http` или `https` (хост не проверяется, Bitbucket может быть корпоративным)
- `branch` и `commit_name` непустые, значения без дефолта, при создании обязательны
- `days` непусты, каждое значение от 1 до 7, повторов нет, после проверки сортируются
- `start_time` и `end_time` разбираются как `HH:MM`, `start_time` строго раньше `end_time`
- `commits_per_day` не меньше 1

`Validate` покрывается табличным тестом `task_test.go`, в таблице валидные тела и по одному случаю на каждое правило выше

## Подключение к базе и ретраи

`db.Connect(dsn, attempts, delay)` в цикле вызывает `gorm.Open` (он сразу пингует базу) и `AutoMigrate`. Каждая неудачная попытка пишется в лог с номером попытки, между попытками пауза `ConnectDelay`. Если за `ConnectAttempts` попыток (по умолчанию 10 по 3 секунды) база не ответила, `main` завершается с ошибкой. HTTP-сервер стартует только после успешного подключения

Это закрывает старт при недоступной базе: контейнер Postgres может подниматься дольше приложения. Если база пропала уже во время работы, процесс не падает: пул `database/sql` сам откроет новые соединения, когда база вернётся, а запросы на время простоя получают 500 с телом `{"error": "..."}` без внутренних деталей

Подключение живёт в `models/db` и принимает `dsn` и числа, а не `config.PGSettings`. Иначе получится цикл импортов: `config` импортирует `models/db` ради типов дефолтов

## Домены

Структуры с зависимостями (`*gorm.DB`, настройки), конструкторы `NewAuth`, `NewTasks`, `NewUsers`. Пакеты-функции из плана 001 больше не годятся, потому что появилась первая зависимость, база

- `Auth`
  - `Register` хеширует пароль (bcrypt), шифрует токен Bitbucket (AES-GCM, случайный nonce в начале значения), вставляет пользователя, выпускает JWT. Дубликат логина ловится через `gorm.Config{TranslateError: true}` и `gorm.ErrDuplicatedKey`
  - `Login` сверяет хеш, выпускает JWT
  - JWT: HS256, claims `sub` (id пользователя) и `exp` (сейчас плюс `TokenTTL`)
  - `Parse` проверяет подпись и срок, возвращает id пользователя
  - Расшифровки токена Bitbucket пока нет, она потребуется с первым вызовом Bitbucket и появится вместе с ним
- `Tasks`: `Create`, `List`, `Get`, `Update`, `Delete`, все принимают id пользователя и работают только с его тасками (условие `id` и `user_id` в запросе)
- `Users`: `List` и `Get`, число тасок считается запросом с `LEFT JOIN tasks` и `GROUP BY users.id`, результат сканируется в `api.UserInfo`

Ошибки домена: `ErrNotFound`, `ErrLoginTaken`, `ErrBadCredentials`, `ErrInvalid` (с текстом). Сервис переводит их в статус-коды, всё остальное даёт 500

## API

Префикс `/api/v1`. Меняется набор методов из плана 001: добавляются два метода users, `/tasks` и `/users` закрываются проверкой JWT

| Метод | Путь | Доступ | Успех | Ошибки |
|---|---|---|---|---|
| POST | `/auth/register` | открыт | 201, cookie | 400, 409 логин занят |
| POST | `/auth/login` | открыт | 200, cookie | 400, 401 |
| POST | `/tasks` | JWT | 201, `Task` | 400 |
| GET | `/tasks` | JWT | 200, массив `Task` | |
| GET | `/tasks/:id` | JWT | 200, `Task` | 404 |
| PUT | `/tasks/:id` | JWT | 200, `Task` | 400, 404 |
| DELETE | `/tasks/:id` | JWT | 204 | 404 |
| GET | `/users` | JWT | 200, массив `UserInfo` | |
| GET | `/users/:id` | JWT | 200, `UserInfo` | 404 |

Любой метод кроме 4xx из таблицы при сбое базы отвечает 500

- `UserInfo`: `id`, `login`, `tasks_count`. Хеш и токен Bitbucket наружу не выходят
- `AuthResult` в ответе register и login: `id`, `login`, `expires_at`. Сам JWT лежит в cookie `token` (HttpOnly, `Expires` по TTL)
- Проверка `Require` читает cookie, вызывает `Auth.Parse`, кладёт id пользователя в `c.Locals`. Без cookie или с битым токеном ответ 401
- Тело ошибки: `{"error": "текст"}`, сервис пишет ошибку в лог через `log/slog`
- Нечисловой `:id` даёт 400

### Как проставляются поля у таски

- Create: берётся `TaskSettings.Params()` (дефолты), поверх разбирается тело. Пропущенное поле остаётся дефолтным, поэтому `{"repo_url": "...", "branch": "main", "commit_name": "..."}` даёт дни 1-5, окно с 09:00 до 18:00, один коммит в день, `active: true`. Явный `"active": false` тоже работает, указатели на `bool` не нужны
- Update (`PUT`): берётся текущая таска из БД, поверх разбирается тело. Пропущенное поле остаётся прежним, так что выключить таску можно телом `{"active": false}`. После слияния выполняется `Validate` и `Save`. `id`, `user_id`, `created_at` остаются как были, `updated_at` обновляет GORM
- Чужая таска и несуществующая таска одинаково дают 404

## Swagger

Аннотации обработчиков заполняются схемами тел (раньше были пустые из-за пустых `models`). Для `Weekdays` и `Clock` в тегах полей указывается `swaggertype`, чтобы в схеме были `array of integer` и `string` с примером `09:00`. Cookie в Swagger 2.0 как схема безопасности не описывается, в UI cookie ставит и отправляет сам браузер. Файл `docs/swagger.json` перегенерируется командой `go generate ./...`

## Postgres в WSL

Контейнера Postgres в WSL сейчас нет. Поднимается один контейнер `footprints-pg` (образ `postgres:17`, порт `5432` проброшен наружу) командой через `wsl -e docker run ...`, логин и пароль из `.env`. Порт 5432 свободен. Приложение запускается в Windows и ходит на `localhost:5432`. Если проброс из WSL не сработает, в `PG_HOST` пойдёт адрес WSL. Остановка и запуск контейнера (`wsl -e docker stop` и `start`) нужны для проверок ретраев

## Принятые решения

Подтверждены по плану в прошлой версии:
- Токен Bitbucket шифруется (AES-GCM, ключ из `AUTH_ENC_KEY`), расшифровка появится с первым использованием
- `PUT` сливает тело с текущими значениями и ведёт себя как частичное обновление
- `/users` и `/tasks` закрыты JWT, любой вошедший видит список всех пользователей
- Окно живёт в пределах одних суток (`start_time` раньше `end_time`), часовой пояс остаётся открытым вопросом из `0004`
- Дефолтное окно с 09:00 до 18:00
- Имена `start_time`, `end_time`, `commit_name` из спеки заменяют `window_start`, `window_end`, `jira_key` из плана 001 и `reference/0004`
- `runs_total` и `last_run_at` откладываются

Добавлено по новым пунктам спеки: настройки сервера в `APISettings`, у таски появилась ветка, работа в ветке `feature/models`, ретраи подключения к базе, ORM вместо SQL-файлов

## Допущения для подтверждения

1. GORM с `AutoMigrate` вместо SQL-схемы и `pgx` напрямую, обоснование выше. Если ближе Bun или что-то ещё, скажи, поменяются только модели и домены
2. `branch` обязательна, дефолта нет. Если нужен, например `main`, он добавляется в `TaskSettings` одной строкой
3. Дни хранятся как `jsonb`, а не `smallint[]`, чтобы не писать свои `Scan` и `Value` (подтверждено)
4. Число попыток и пауза между ними задаются через `PG_CONNECT_ATTEMPTS` и `PG_CONNECT_DELAY`, по умолчанию 10 и 3 секунды. После исчерпания попыток приложение завершается с ошибкой (подтверждено)
5. Во время работы при пропавшей базе запросы получают 500, отдельного статуса 503 нет, дополнительной обработки не вводим (подтверждено)

## Проверка

Сборка: `go build ./...`, `go vet ./...`, `go test ./...`, `go generate ./...` без ошибок

Табличный тест `Validate` (до запуска сервера): валидные тела проходят, каждое нарушенное правило (день 0 и 8, повтор дня, пустые дни, `start_time` позже или равен `end_time`, время `25:00`, пустые `repo_url`, `branch`, `commit_name`, URL без схемы, `commits_per_day` 0) возвращает ошибку, `9:00` нормализуется в `09:00`, дни сортируются

Сценарий через `curl` (cookie в файлах `-c` и `-b`), сервер запущен локально, восемь шагов:
1. Авторизация: два пользователя, регистрация даёт 201 и `Set-Cookie: token`, повторный логин даёт 409, вход с неверным паролем даёт 401, запрос `/tasks` без cookie даёт 401
2. Создание тасок: тело из трёх полей (`repo_url`, `branch`, `commit_name`) даёт в ответе дни `[1,2,3,4,5]`, окно `09:00` и `18:00`, один коммит, `active` true. Полное тело (`days: [1,3,5]`, `start_time: "9:00"`, три коммита, `active: false`) сохраняется как задано, время приведено к `09:00`
3. Валидация через API: на `POST` и на `PUT` тела с днём 8, `start_time` позже `end_time`, пустой `branch`, `commits_per_day` 0 и битым JSON дают 400, новая таска не создаётся, существующая остаётся прежней
4. Редактирование: `PUT {"active": false}` меняет только `active` и `updated_at`. `PUT {"days": [2,4], "commits_per_day": 2, "branch": "dev"}` меняет только эти поля, остальные прежние
5. Изоляция и users: таска первого пользователя недоступна второму (GET, PUT, DELETE дают 404), `GET /tasks` отдаёт только свои. `GET /users` показывает обоих с верным `tasks_count`, `GET /users/:id` работает и даёт 404 для несуществующего. После `DELETE` таски (204) её `GET` даёт 404, а `tasks_count` уменьшился

7. Ретраи при старте: остановить контейнер, запустить сервер, в логе видны неудачные попытки с паузой, процесс жив. Через 10 секунд запустить контейнер, сервер подключается, мигрирует схему и отвечает на запросы
8. Падение базы во время работы: при работающем сервере остановить контейнер, запрос отвечает 500 с телом ошибки, процесс жив. Запустить контейнер, следующие запросы снова успешны без перезапуска сервера
