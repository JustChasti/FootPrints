# План 004: настоящие коммиты в Bitbucket

Основание: `spec.md`. Задача: заменить заглушку `push` в `core/push.go` настоящим коммитом через REST API Bitbucket, по пути 1 из `reference/0001-git-via-bitbucket-rest-api.md`. Файл для коммита генерируется на лету: имя это обрезанный хэш с расширением `.txt`, внутри 32-64 строки случайных хэшей. Работа идёт в ветке `feature/real-commits`

## Что выяснилось по токену и как это меняет план

В спеке сказано, что по токену из `api-key.txt` можно создать репозиторий и сделать пару коммитов, а на проде токен другой, короткий и Bearer. Проверка показала, что токен из файла начинается с `ATATT3`: это личный API-токен Atlassian Cloud. Два запроса к `api.bitbucket.org` (`GET /2.0/user` и `GET /2.0/workspaces`) с заголовком `Authorization: Bearer` вернули 401 «Token is invalid, expired, or not supported for this endpoint». Cloud принимает такой токен только как Basic `email:токен`. Bearer-токены Cloud (workspace и repository access tokens) требуют платного тарифа, проверить это нельзя

Решение по итогам разговора: боевая цель это Bitbucket Server (закрытый контур, Bearer), и она описана в `0001`. Реализуем только её. Вживую проверяет пользователь после переноса в контур, а здесь она проверяется на локальной подделке Bitbucket (раздел «Проверка»). Bitbucket Cloud не реализуется, токен из `api-key.txt` дальше этих двух запросов не используется. Если позже понадобится живая проверка на Cloud, нужны email аккаунта и отдельная ветка клиента, в этот шаг она не входит

## Как учтены дописки спеки

| Дописка | Решение |
|---|---|
| Работать с Bitbucket, токен в `api-key.txt` | Токен оказался API-токеном Cloud, см. раздел выше. Server-клиент по `0001`, проверка на подделке |
| Создать репу и сделать пару коммитов | Живой Cloud недоступен. Репозиторий не создаём, коммиты проверяются на подделке сервера и затем пользователем на проде |
| Файл это обрезанный хэш в формате txt | Имя `<первые 12 символов sha256 содержимого>.txt`, раздел «Файл коммита» |
| Внутри от 32 до 64 строк случайных хэшей | Число строк случайное от 32 до 64 включительно, каждая строка это sha256 в hex от случайных байт |
| Изменения в ветке `feature/real-commits` | Создаётся от `main` первой задачей |
| Адрес `.../projects/PROJ/repos/repo-name/browse` превращается в `.../rest/api/1.0/projects/PROJ/repos/repo-name` | `repoAPIURL` делает это преобразование, клиент добавляет `/browse/<путь файла>`. Версия API `1.0` из спеки (в `0001` был `latest`) |

## Что входит

- Клиент Bitbucket Server REST в `core/bitbucket.go`: разбор `repo_url` и один запрос `PUT .../browse/{path}` на коммит
- Настройка `BITBUCKET_API_VERSION` (по умолчанию `1.0`) в `config/config.go` и строка в `.env.example`
- Генератор файла в `core/content.go`
- Настоящий `push` в `core/push.go` вместо заглушки: берёт токен владельца таски, расшифровывает, делает коммит, возвращает id коммита
- Расшифровка токена: метод `Auth.DecryptToken` в `domains/auth.go`, парный к `encrypt`
- Колонка `commit_id` в `planned_commits`, запись id при успешном пуше
- Тесты: генератор файла, разбор адреса, клиент на `httptest`, шифрование туда и обратно
- Прогон на живой базе против локальной подделки Bitbucket Server
- Обновление `reference/0001`, `reference/0002`, `README.md`, примера `repo_url` в Swagger

Вне шага: Bitbucket Cloud, создание репозиториев и веток, повторы неудачных коммитов, валидация `repo_url` в API, вывод `commit_id` в API, очистка старых `planned_commits`, живая проверка на настоящем Server (её делает пользователь)

## Клиент Bitbucket Server

Запрос по `0001`, один на коммит:

```
PUT https://<host>/rest/api/<версия>/projects/<KEY>/repos/<slug>/browse/<path>
Authorization: Bearer <токен>
X-Atlassian-Token: no-check
Content-Type: multipart/form-data
  content = <тело файла>
  message = <commit_name таски>
  branch  = <ветка таски>
```

`sourceCommitId` не передаём: файл всегда новый. Ответ 200 содержит JSON с полем `id`, это id созданного коммита. Автора коммита Bitbucket берёт из владельца токена

Разбор `repo_url` (`repoAPIURL(repoURL, apiVersion) (string, error)`, чистая функция) превращает адрес из браузера в адрес REST API. Пример из спеки при версии по умолчанию `1.0`:

```
https://bitbucket.example.com/projects/PROJ/repos/repo-name/browse
https://bitbucket.example.com/rest/api/1.0/projects/PROJ/repos/repo-name
```

Первая строка это `repo_url` в таске, вторая результат. Алгоритм: путь режется на сегменты, первые четыре должны быть `projects`, `<KEY>`, `repos`, `<slug>`, остальной хвост (`/browse`, `/browse/dir`, `?at=...`) отбрасывается. Результат это `<схема>://<хост[:порт]>/rest/api/<версия>/projects/<KEY>/repos/<slug>`, клиент дописывает к нему `/browse/<путь файла>`. Версию функция получает параметром, значение приходит из конфига

Один вид адреса, как в спеке. Всё остальное, в том числе адрес Cloud `https://bitbucket.org/team/repo`, адрес клона `/scm/KEY/slug.git`, личные репозитории `/users/...` и Bitbucket с контекстным путём перед `/projects`, даёт ошибку `unsupported repo_url`. Запись получает `failed` с этим текстом. Другие виды добавим, когда они встретятся на проде. Валидацию в API этим шагом не меняем: нерабочий адрес сразу виден в `error`

Устройство клиента:
- Структура `bitbucket` с полем `client *http.Client` и методом `commitFile(apiURL, token, branch, path, message, body) (string, error)`, где `apiURL` это результат `repoAPIURL`. Интерфейса нет, тесты подставляют `httptest`-сервер и свой клиент
- `http.Client{Timeout: 30 * time.Second}`, константа в коде. Пуш не отменяется через `ctx` (решение шага 003), поэтому таймаут единственное, что не даст зависшему запросу держать остановку сервиса
- Тело ответа при ошибке читается через `io.LimitReader` на 512 байт. Ошибка имеет вид `bitbucket answered 403: <текст>` и попадает в `planned_commits.error`
- Успехом считается любой статус 2xx (в `0001` описан 200, но 201 тоже не должен ронять коммит)
- Статус 2xx без разбираемого `id`: пуш считается удавшимся, `commit_id` остаётся пустым, в лог пишется предупреждение. Коммит уже мог появиться, и помечать его неудачным было бы неверно
- Повторов нет, как в 003: неудача это `failed` на этот день
- Токен не попадает в логи и тексты ошибок. Ошибки `net/http` содержат адрес запроса, но не заголовки

## Файл коммита

`newFile(now time.Time) (path string, body []byte)`:
- число строк `n` случайное от 32 до 64 включительно (`rand.IntN(33) + 32`)
- каждая строка это `hex(sha256(32 случайных байта из crypto/rand))`, 64 символа, в конце файла перевод строки
- имя файла это первые 12 символов `hex(sha256(body))` плюс `.txt`. Содержимое случайное, поэтому имена не совпадают, 12 символов это 48 бит
- путь `autocommit/<yyyy-mm-dd>/<имя>.txt`, дата по времени сервера. Папка по дате взята из `0001`, она не засоряет корень репозитория

## Токен и push

`push` становится методом `Core`, потому что ему нужны база, расшифровка и клиент:

```go
func (c *Core) push(task db.Task) (string, error) {
    // владелец таски: First(&user, task.UserID), Select("bitbucket_token")
    // token, err := c.decrypt(user.BitbucketToken)
    // apiURL, err := repoAPIURL(task.RepoURL, c.apiVersion)
    // path, body := newFile(time.Now())
    // return c.bb.commitFile(apiURL, token, task.Branch, path, task.CommitName, body)
}
```

- `core.New(gdb, tickInterval, apiVersion, decrypt)`: `apiVersion` это строка из `cfg.Bitbucket.APIVersion`, `decrypt` это `func([]byte) (string, error)`. Значения передаются в конструктор, как в `db.Connect`, пакет настроек не нужен. В `main.go` передаются `cfg.Bitbucket.APIVersion` и `authDomain.DecryptToken`. Пакет `core` по-прежнему не импортирует `domains` и `config`
- Токен берётся отдельным запросом на каждый пуш. Это один дешёвый `SELECT` на коммит, `Joins("Task.User")` усложнил бы выборку записей ради нуля выгоды
- Любая ошибка (нет пользователя, не расшифровался токен, плохой адрес, ответ Bitbucket) возвращается из `push` и ложится в `error` записи со статусом `failed`
- `execute` при успехе пишет в запись `commit_id` вместе со статусом `done`

## domains: DecryptToken

```go
func (a *Auth) DecryptToken(enc []byte) (string, error)
```

Обратная операция к `encrypt`: nonce в начале, `aead.Open` по остатку. Если длина меньше размера nonce, возвращается ошибка, паники нет. Тест `domains/auth_test.go`: шифрование и расшифровка дают исходную строку, испорченный шифротекст и короткий вход дают ошибку, два шифрования одной строки дают разные байты (nonce случайный)

## Конфиг

Новая структура `BitbucketSettings`, поле `Bitbucket` в `Config`. Имя `APISettings` уже занято адресом самого сервиса, поэтому структура названа по Bitbucket

| Структура | Поле | Откуда | Значение по умолчанию |
|---|---|---|---|
| `BitbucketSettings` | `APIVersion` | `BITBUCKET_API_VERSION` | `1.0` |

Значение подставляется в путь `/rest/api/<версия>/` как есть, пустая переменная оставляет значение по умолчанию (так работает `envString`). Проверки формата нет: настройку задаёт тот, кто разворачивает сервис, а неверное значение сразу видно в `error` записи как ответ Bitbucket 404. В `.env.example` добавляется строка с комментарием. `core.New` принимает версию строкой (раздел «Токен и push»), `config` и `core` по-прежнему не знают друг о друге

## Шифрование токена

Шифруется токен Bitbucket, который инженер вводит при регистрации, и шифруется для хранения в базе. Так устроено с шага 002: `Register` кладёт в `users.bitbucket_token` шифротекст AES-GCM, ключ берётся из `AUTH_ENC_KEY`. Расшифровка нужна один раз на пуш, чтобы подставить токен в заголовок запроса

Запросы к Bitbucket этот шаг ничем не шифрует и не подписывает. На проде они идут по HTTPS, канал защищает TLS. Токен уходит в заголовке `Authorization: Bearer` в том виде, в каком его выдал Bitbucket. В открытом виде он живёт только в памяти сервиса на время одного запроса и не попадает ни в логи, ни в тексты ошибок

Следствие: ключ шифрования один на сервис, поэтому после смены `AUTH_ENC_KEY` сохранённые токены перестают расшифровываться, а пуши по ним получают `failed` с ошибкой расшифровки

## Особенности и принятые следствия

- Шифрование относится к токену, который лежит в базе (раздел «Шифрование токена»). Запросы к Bitbucket идут по HTTPS без шифрования на стороне сервиса
- Пока `repo_url` разбирается только под Server, регистрация и создание таски проходят с любым http(s) адресом, ошибка проявится на коммите. Это следствие решения не трогать валидацию в этом шаге
- Ветка таски должна уже существовать в репозитории. Сервис ничего не создаёт, при отсутствии ветки ответ Bitbucket ляжет в `error`
- Защита ветки, обязательный PR и хуки Bitbucket применяются и к REST-коммитам (`0001`). Ответ 4xx с текстом хука виден в `error`
- Rate limit на стороне Bitbucket возможен, повторов нет, неудачный слот остаётся `failed`

## Допущения для подтверждения

1. Только Bitbucket Server по `0001`, Cloud не реализуем, `api-key.txt` не используется (обоснование в начале плана)
2. Путь файла `autocommit/<yyyy-mm-dd>/<12 hex>.txt`: папка по дате взята из `0001`, спека папку не упоминает. Если нужен файл в корне репозитория, это правка одной строки
3. Имя файла это первые 12 символов sha256 его содержимого, строки внутри это полные sha256 в hex
4. Сообщение коммита это `commit_name` таски, одинаковое для всех коммитов таски
5. Версия API в пути по умолчанию `1.0`, как в спеке (в `0001` стоял `latest`), меняется настройкой `BITBUCKET_API_VERSION`. Формат значения не проверяется
6. Заголовок `X-Atlassian-Token: no-check` отправляем всегда: Atlassian требует его для multipart-запросов, если сервер принимает их за браузерные, а лишним он не бывает. Если твой curl на проде работал без него и он мешает, уберём
7. Адрес `repo_url` один вид, как в спеке: `<схема>://<хост>/projects/KEY/repos/slug[/browse...]`. Остальные виды (клон `/scm/...`, личные репозитории `/users/...`, контекстный путь) дают `unsupported repo_url`, добавим по мере появления
8. Таймаут запроса 30 секунд, повторов нет
9. Ответ 200 без `id` считается успехом с пустым `commit_id` и предупреждением в логе
10. Валидацию `repo_url` в API не меняем
11. Шифруется токен, введённый инженером, и только в базе. Запросы к Bitbucket дополнительно не шифруются и не подписываются, их защищает HTTPS

## Проверка

Сборка: `go build ./...`, `go vet ./...`, `go test ./...`, `go generate ./...` без ошибок, в `docs/swagger.json` новый пример `repo_url`

Тесты на чистых функциях и `httptest`:
- `newFile`: на сотне вызовов число строк всегда от 32 до 64, каждая строка 64 символа hex, файл оканчивается переводом строки, путь подходит под `^autocommit/\d{4}-\d{2}-\d{2}/[0-9a-f]{12}\.txt$`, имя совпадает с началом sha256 тела, два вызова дают разные пути
- `repoAPIURL`: адрес из спеки `https://bitbucket.example.com/projects/PROJ/repos/repo-name/browse` даёт `https://bitbucket.example.com/rest/api/1.0/projects/PROJ/repos/repo-name`; тот же адрес без `/browse`, с хвостом `/browse/dir?at=refs/heads/x`, с портом в хосте, со схемой `http` (схема и порт сохраняются); ошибки: адрес Cloud `https://bitbucket.org/team/repo`, адрес клона `/scm/KEY/slug.git`, `/users/name/repos/slug`, контекстный путь `/bitbucket/projects/...`, пустой ключ или slug, слишком короткий путь. Версия берётся из параметра: с `2.0` в результате `/rest/api/2.0/`
- `commitFile` против `httptest`-сервера: метод `PUT`, путь `/rest/api/1.0/projects/KEY/repos/slug/browse/<path>`, заголовок `Authorization: Bearer <токен>`, поля формы `content`, `message`, `branch`; ответ 200 с `{"id":"abc"}` даёт `abc`; ответ 403 с телом даёт ошибку с кодом и текстом; длинное тело ошибки обрезается до 512 байт; ответ 200 с `{}` даёт пустой id без ошибки; сервер, который держит запрос дольше таймаута клиента (клиент в тесте с таймаутом 50 мс), даёт ошибку
- `DecryptToken`: см. раздел выше

Сценарий на живой базе, Postgres в WSL как в плане 003 (перед запуском разбудить WSL и держать его фоновым `sleep 3600`, дождаться `pg_isready` и открытого порта). Локальная подделка Bitbucket Server, маленькая Go-программа в каталоге scratchpad вне репозитория: принимает `PUT /rest/api/{версия}/projects/{KEY}/repos/{slug}/browse/{path}` (версию пишет в лог), проверяет `Authorization: Bearer test-bb-token`, разбирает форму, пишет каждый запрос строкой JSON в файл (путь, ветка, сообщение, число строк в файле, все ли строки по 64 hex) и отвечает по ключу проекта: `OK` 200 с `{"id":"<случайный sha1>"}`, `DENY` 403 с JSON ошибки Bitbucket, `NOID` 200 с `{}`. Сервис запускается с `CORE_TICK_INTERVAL=10s`, окна тасок на ближайшие две-три минуты:
