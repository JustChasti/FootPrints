# План 003: фоновая горутина и ядро core/

Основание: `spec.md`. Задача: добавить в `core/` фоновую горутину, которая раз в период находит запланированные коммиты, пришедшие ко времени, и вызывает функцию пуша. Пока пуш это заглушка, коммит в Bitbucket появится отдельным шагом. Расписание строится по `reference/0004-schedule-work-window-instead-of-cron.md` (рабочее окно и число коммитов в день), хранилище Postgres через GORM по `reference/0005-orm-gorm-automigrate.md`

Это вторая версия плана, после дописок в спеке. Главное изменение: расписание хранится в таблице `planned_commits` из `0004`, полей состояния в таске (как в первой версии) больше нет

Считается при чтении в Go по записям, подгруженным через `Preload`, в таблице тасок не хранится (раздел «Счётчики и последний запуск в API») |

## Расписание: planned_commits вместо состояния в таске

Идея из спеки: у таски статус и ближайшее время, раз в день в заданный час статусы обнуляются, дальше опрос выполняет таски, пришедшие ко времени, и переставляет время. Первая версия плана сохраняла её основу и держала состояние тремя полями в таске (`commits_today`, `next_run_at`, `planned_day`). Дописки спеки меняют расклад, поэтому сравниваю заново

| | Состояние в таске (версия 1) | `planned_commits` (версия 2) |
|---|---|---|
| Неудачный пуш без перепланирования | отдельный счётчик в таске и логика "не двигать время" | строка со статусом `failed`, остальные строки дня живут как жили |
| Счётчик неудачных по таске | новое поле | `count` по таблице, поля нет |
| Выбор времён | цепочка: после каждого запуска случайное время между now и концом, нужна формула минимума из `k` точек, иначе коммиты сбиваются к концу окна | на сетке в 10 минут выбираем `n` разных слотов случайно, формулы нет |
| Защита от затирания | `Omit` в `Tasks.Save`, `UpdateColumns` в горутине, иначе `PUT` и горутина перетирают друг друга | таска не меняется, вопроса нет |
| Статистика `done_commits`, `failed_commits`, `last_run_at` | отдельная таблица запусков, её в плане нет | считается из этой же таблицы |
| Рестарт и простой | состояние в таске, достаточно | состояние в таблице, достаточно |
| Цена | три поля в `Task`, `Omit`, формула | одна таблица, один `INSERT` на день по таске, один `UPDATE` на коммит |

Версия 2 теперь проще и это решение уже принято в `0004`. Версия 1 была проще, пока не было счётчика неудач, сетки и статистики. Проигрыш версии 2 один: счётчики в ответах API приходится считать запросом к таблице. Для `done_commits`, `failed_commits` и `last_run_at` это `Preload` записей таски и подсчёт в Go (раздел «Счётчики и последний запуск в API»). Нужны они редко, лишний запрос ничего не стоит, SQL с `JOIN` и агрегатами в коде не появляется. Поля `commits_today` и `next_run_at` из версии 1 в API не выводятся, в спеке они не нужны

Утренний час из спеки по-прежнему заменён планированием при опросе: каждый опрос сам проверяет, спланирован ли у активной таски сегодняшний день, и если нет, планирует. Плюсы те же: рестарт в 8:05 день не теряет, окно раньше 8:00 не ломается, таска, созданная посреди дня, планируется на остаток окна, лишней настройки нет. Если нужен именно час, это условие "не раньше этого часа" на шаге планирования

## Таблица planned_commits

```go
type PlannedCommit struct {
    ID         int64      `gorm:"primaryKey"`
    TaskID     int64      `gorm:"not null;uniqueIndex:idx_planned_task_at"`
    Task       *Task
    PlannedAt  time.Time  `gorm:"not null;uniqueIndex:idx_planned_task_at;index"`
    Status     CommitStatus `gorm:"not null;default:planned"`
    ExecutedAt *time.Time
    Error      string     `gorm:"not null;default:''"`
}
```

- Файл `models/db/planned_commit.go`, рядом тип `CommitStatus` с константами статусов (см. `reference/0008-typed-string-constants.md`). `AutoMigrate` в `connect.go` получает `&PlannedCommit{}` после `User` и `Task`
- Статусы: `planned` (ждёт времени), `done` (пуш прошёл), `failed` (коммита нет: пуш вернул ошибку или запись просрочена и пуш не делался, причина в `Error`)
- Два момента времени в записи: `PlannedAt` это плановое время слота, оно ставится при планировании и больше не меняется (по нему индекс, выборка "пора выполнять", проверка "спланирован ли сегодня" и проверка просрочки). `ExecutedAt` это фактическое время запуска пуша
- `ExecutedAt` заполняется, когда пуш запускался: у `done` и у `failed` после ошибки пуша. У `planned` и у просроченных `failed` пусто, пуш в них не делался, поэтому `last_run_at` показывает только настоящие запуски. Имя `ExecutedAt` вместо `done_at` из схемы `0003` выбрано потому, что для неудачной записи слово "выполнена" не подходит, а время запуска нужно для `last_run_at`
- Уникальный индекс `(task_id, planned_at)` защищает от двойного планирования и от двух коммитов в один слот
- Каскад: при удалении таски её записи уходят вместе с ней. Ограничение задаётся тегом на связи `Task.PlannedCommits` (следующий раздел), на стороне "много". Тег на `PlannedCommit.Task` не нужен: по моим сведениям, при парной связи GORM берёт ограничение оттуда. Проверяется на живой базе
- Поле `PlannedCommit.Task` нужно для `Joins("Task")` на шаге запуска, связь `Task.PlannedCommits` для подгрузки записей при чтении тасок. `commit_id` из схемы `0003` добавится вместе с настоящим пушем
- В `Task` добавляются связь `PlannedCommits` и три вычисляемых поля (следующий раздел), остальное в `Task` не меняется

## Счётчики и последний запуск в API

В `db.Task` добавляются связь для подгрузки записей и три вычисляемых поля:

```go
PlannedCommits []PlannedCommit `json:"-" gorm:"constraint:OnDelete:CASCADE"`

DoneCommits   int        `json:"done_commits"   gorm:"-" example:"3"`
FailedCommits int        `json:"failed_commits" gorm:"-" example:"0"`
LastRunAt     *time.Time `json:"last_run_at"    gorm:"-"`
```

- Значения считаются при чтении по связанным записям, в таблице тасок их нет. Тег `gorm:"-"` обычное "ORM поле не трогает": не читает, не пишет, не мигрирует
- `done_commits` это число записей `planned_commits` со статусом `done` по таске, `failed_commits` число записей `failed`. Вместе они показывают, что прошло три дня, коммит один, а остальные пуши упали. Просроченные записи (пуш не делался) тоже считаются в `failed_commits`: коммит не появился, а причину, ошибку пуша или простой сервиса, показывает текст в `error`
- `last_run_at` это время последнего запуска пуша, максимум `executed_at` по записям таски (`done` и `failed` вместе), `null` если запусков ещё не было. Если последняя попытка была неудачной, а предыдущая удачной, `last_run_at` покажет неудачную, различить их можно по счётчикам
- `Get` и `List` в `domains/tasks.go` подгружают записи через `Preload("PlannedCommits", func(db *gorm.DB) *gorm.DB { return db.Select("task_id", "status", "executed_at") })` и вызывают для каждой таски `FillStats`. Это два запроса вне зависимости от числа тасок, SQL-фрагментов с `JOIN` и агрегатами нет
- `Task.FillStats()` в `models/db/task.go`: один проход по `PlannedCommits`, считает записи `done` и `failed`, берёт максимум `ExecutedAt`. Чистая функция без базы, проверяется табличным тестом
- Ловушка GORM: `Save` по умолчанию записывает и связанные записи, а подгруженные записи неполные (без `id` и `planned_at`) и ушли бы в `INSERT`. Поэтому `Tasks.Save` получает `Omit(clause.Associations)`
- `Create` отдаёт нули и `null`. `PUT` берёт таску через `Get`, поэтому значения в его ответе актуальны
- Поля видны во всех ответах по таскам. Тело `POST` и `PUT` разбирается в `TaskParams`, поэтому клиент их задать не может. В Swagger схема `db.Task` получает три поля, `docs/swagger.json` перегенерируется
- Подгружается вся сохранённая история записей таски: сегодня это сотни строк в год на таску, после очистки из следующего шага (два месяца) не больше пары сотен
- Проверить на реальной базе: что `Preload` с `Select` отдаёт нужные колонки, что `Save` не пишет связь, что `AutoMigrate` не создаёт колонок под вычисляемые поля и делает ровно один внешний ключ с каскадом

## Users без сырого SQL

Сейчас `domains/users.go` собирает один запрос `query()` из строк: `Table("users")`, `Select("... count(tasks.id) AS tasks_count")`, `Joins("LEFT JOIN tasks ...")`, `Group`. Это правка ради единого стиля с остальным шагом, поведение и ответы API не меняются

- `List`: `Find(&users)` по модели `db.User` с `Order("id")` и один запрос `Model(&db.Task{}).Pluck("user_id", &owners)`: список id владельцев всех тасок. Счётчики набираются в Go проходом по списку (`counts[id]++`), у пользователя без тасок в карте нет записи, то есть счётчик 0
- `Get`: `First(&user, id)` и `Model(&db.Task{}).Where("user_id = ?", id).Count(&n)`. Ошибка "не найден" переводится в `ErrNotFound` так же, как в `domains/tasks.go`
- Хелпер `query()` исчезает, `api.UserInfo` собирается из `db.User` и счётчика. SQL-строк с агрегатами, `JOIN` и `COALESCE` нет: тот же подход, что у счётчиков тасок, загрузить и посчитать в Go. `Pluck` тянет один столбец по всем таскам, для объёма сервиса это ничего не стоит
- После этого шага в проекте остаются только условия с плейсхолдерами (`Where("user_id = ?", id)`, `First(&x, "login = ?", ...)`), это обычный стиль GORM. Условия структурой не используем: они пропускают нулевые значения, и `GET /tasks/0` вернул бы первую таску пользователя
- Связь `User.Tasks` не добавляется: она образовала бы пару с существующей `Task.User` и тронула бы внешний ключ, ради подсчёта числа тасок это лишнее
- Цена: около 15 строк вместо 10 и два запроса вместо одного

## Сетка и слоты

Шаг сетки равен `TickInterval`. Сетка привязана к часам: точки `10:00`, `10:10`, `10:20` (при шаге 10 минут). Опросы тоже просыпаются на этих точках, поэтому запись на `10:20` выполняется на опросе в `10:20`

Слоты таски на дату `D`: точки сетки `t`, для которых `first <= t < end`, где
- `start` и `end` это `start_time` и `end_time` таски на дату `D` (`Clock.At`), в поясе сервера
- `first = max(start, now.Truncate(step))`, для `start` не на сетке слот округляется вверх (`09:05` даёт первый слот `09:10`). Точка `now.Truncate(step)` допускается, чтобы слот текущего опроса не пропадал
- `end` исключается: коммит ровно в конец окна уже после окна
- если сегодняшний день недели (ISO, 1-7) не входит в `days`, слотов нет

Выбор: `n = min(commits_per_day, число слотов)`, `n` разных слотов случайно, сортируются. Если слотов меньше, чем коммитов в день (узкое окно), планируется столько, сколько есть. Валидацию "окно вмещает число коммитов" в API этот шаг не добавляет

## Алгоритм опроса

`tick(now)`, `now` берётся один раз на опрос. Два шага подряд, поэтому слот текущего опроса, выбранный на первом шаге, выполняется на втором в тот же опрос

### Шаг 1: планирование дня

Выбираются активные таски, у которых нет записей `planned_commits` с `planned_at` за сегодня. "Активная" значит `active = true` в самой таске: это поле из `TaskParams` (по умолчанию `true`), инженер выключает таску через `PUT {"active": false}`. Выключенная таска не планируется и не запускается, отдельной проверки в ядре нет, только условие `WHERE active` в запросах. Выборка двумя запросами без `NOT EXISTS`: `Pluck` id тасок, у которых есть записи за сегодня (`Model(&PlannedCommit{}).Where("planned_at >= ? AND planned_at < ?", ...).Distinct().Pluck("task_id", &ids)`), и `Find` активных тасок. Таски, чей id есть в первом списке, пропускаются в Go. `NOT IN` в запросе не используется: на пустом списке GORM превращает его в `NOT IN (NULL)`, и запрос ничего не находит. Сутки считаются по времени сервера, от 00:00 до 00:00 следующего дня. Сброса как отдельного действия нет: с началом новых суток вчерашние записи перестают попадать в "сегодня", и первый опрос после полуночи (по сетке это 00:00) находит у таски пустой день и планирует его. Старые записи не удаляются, это история и источник счётчиков. Для каждой считаются слоты и выбираются `n` из них, записи вставляются пачкой. Если слотов нет (не её день, окно закрыто), ничего не пишется, такая таска проверяется на каждом опросе и это ничего не стоит

### Шаг 2: запуск

Записи выбираются через `Joins("Task")` (связь `PlannedCommit.Task`): `status = 'planned'`, `planned_at <= now`, таска активна, порядок по возрастанию `planned_at`. Присоединённая таска сразу лежит в записи. Как GORM называет алиас присоединённой таблицы в Postgres (регистр в условии на `active`), проверяется на живой базе. Для каждой:
1. Если процесс получил сигнал остановки, цикл прерывается, оставшиеся записи ждут следующего старта
2. Запись просрочена, если `planned_at` раньше начала сегодняшних суток или `now` не раньше `end_time` таски на сегодня. Ставится `failed`, в `Error` причина (`просрочена: запись из прошлых суток` или `просрочена: окно закрыто`), `executed_at` остаётся пустым, пуш не делается, в лог пишется предупреждение. Это защита от коммитов ночью после простоя и от вчерашних записей
3. Иначе вызывается `push(task)`. Успех: `done` и `executed_at = now`. Ошибка: `failed`, `executed_at = now`, `Error` с текстом, запись в лог на уровне error. Повтора нет

Просроченная в пределах окна запись (сервис лежал с 10:00 до 12:00, запись была на 10:30) выполняется на первом опросе после старта, окно ещё открыто

Записи неактивных тасок выпадают из выборки и остаются `planned`. Если таску включить снова, они либо выполнятся (окно ещё открыто), либо станут просроченными `failed` на ближайшем опросе

## Горутина: цикл и остановка

`Core.Run(ctx)`: первый опрос сразу при старте, дальше цикл: ждать до ближайшей точки сетки (`time.Until(now.Truncate(step).Add(step))`) или отмены `ctx`, выполнить опрос. Если опрос затянулся дольше периода, следующий ждёт ближайшую точку после его окончания, пересечения нет

Остановка:
- `main` создаёт `ctx` через `signal.NotifyContext` на `os.Interrupt` и `SIGTERM`
- Горутина проверяет `ctx` между записями (шаг 2) и в ожидании между опросами. Пуш, который уже идёт, доделывается до конца: `ctx` в `push` и в запросы к базе не передаётся, иначе прерванный пуш оставил бы неизвестное состояние. Запись статуса после пуша тоже выполняется
- Веб-сервер останавливается тем же `ctx`: `app.Listen(addr, fiber.ListenConfig{GracefulContext: ctx})`. Без этого перехват сигнала оставил бы сервер без остановки
- `main` после выхода из `Listen` отменяет `ctx` (это же покрывает ошибку запуска сервера, например занятый порт) и ждёт завершения горутины через канал, потом выходит. Ошибку `Listen`, если она была, возвращает в лог и завершается с кодом 1
- Сбой между пушем и записью статуса (например, убили процесс): запись остаётся `planned` и после рестарта выполнится снова. Для случайных коммитов это допустимо, дубль безвреден

## Структура

```
core/
  core.go            Core, New, Run (цикл с выравниванием), tick (планирование и запуск)
  schedule.go        чистые функции: slots, pick, overdueReason
  schedule_test.go   табличные тесты расписания
  push.go            заглушка push(task), на её месте будет коммит в Bitbucket
models/db/
  planned_commit.go  PlannedCommit, статусы
  task.go            Clock.At, связь PlannedCommits, поля DoneCommits, FailedCommits, LastRunAt, метод FillStats
domains/
  tasks.go           Get и List подгружают записи (Preload) и вызывают FillStats, Save с Omit(clause.Associations)
  users.go           List и Get через Find и Count без сырого SQL
```

- `core` импортирует `models/db` и `gorm`, настройки принимает числом (`New(gdb, tickInterval)`), как `db.Connect`. Слоя `domains` между ним и базой нет, ядро работает с `*gorm.DB` напрямую, как домены
- Логика расписания чистыми функциями: `slots(task, now, step)` отдаёт точки сетки, `pick(slots, n)` случайные `n`, `overdueReason(task, plannedAt, now)` проверка просроченной записи. Без базы, поэтому проверяются табличным тестом. Работу с базой делает только `tick`
- `push(task db.Task) error` пишет в `slog` id таски, репозиторий, ветку и имя коммита, возвращает `nil`. Расшифровки токена и вызова Bitbucket пока нет
- В `models/db/task.go` добавляется `Clock.At(day time.Time) (time.Time, error)`: время суток на дату `day` в её поясе, поверх существующего `minutes()`. Значения в базе прошли `Validate`, ошибка возможна только при порче данных, тогда таска пропускается с записью в лог

## main.go

После `db.Connect`:

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

done := make(chan struct{})
go func() {
    defer close(done)
    core.New(gdb, cfg.Core.TickInterval).Run(ctx)
}()

stop()
<-done
if err != nil { log.Fatal(err) }
```

Это набросок, детали (например, ждёт ли `Listen` завершения запросов при `GracefulContext` в `fiber v3.6.0`) проверяются при реализации. Ошибки в горутине (выборка, запись) пишутся в лог, опрос продолжается на следующей точке, процесс не падает

## Особенности и принятые следствия

- Время сервера. Окно и дни недели считаются в `time.Local` процесса, в контейнере это обычно UTC. Закрывает часть открытого вопроса из `0004` про часовой пояс, отдельное поле таски не заводится
- Правка расписания таски через `PUT` посреди дня вступает в силу со следующего дня: записи на сегодня уже вставлены. Исключение `active`, выключенная таска выпадает из выборки сразу
- Просроченными становятся и оставшиеся записи таски, которую выключили посреди дня и включили позже: при включении они получат `failed` и попадут в `failed_commits`
- Рассчитано на один экземпляр сервиса (`replicas: 1`, см. `0003`), блокировок выбора нет
- Все таски, у которых слот на одну точку, запускаются в одном опросе по очереди, параллелизма нет
- Выравнивание опроса по сетке считается от абсолютного времени, для часовых поясов со смещением не кратным шагу сетка сдвинется. Серверу это не мешает, пояса с такими смещениями не рассматриваются

## Допущения для подтверждения

1. `planned_commits` вместо полей состояния в таске, обоснование в таблице выше (подтверждено)
2. Счётчики считаются в Go по записям `planned_commits`, подгруженным `Preload` (`done` для `done_commits`, `failed` для `failed_commits`), хранимых полей в таске нет. SQL с `JOIN` и агрегатами в коде не пишем (решено после обсуждения). В API выводятся полями `done_commits`, `failed_commits` и `last_run_at` (по записям в спеке). Просроченные записи считаются в `failed_commits`
3. `last_run_at` это время последней попытки пуша, удачной или нет (так в README: "когда был последний запуск") (подтверждено)
4. Опросы выравниваются по сетке, шаг сетки равен периоду опроса, по умолчанию 10 минут, через `CORE_TICK_INTERVAL` меняется для проверки. Запись на `10:20` выполняется на опросе в `10:20`, фаза опросов от момента запуска сервиса не зависит (подтверждено)
5. Конец окна исключается из слотов, последний слот при окне `09:00-18:00` и шаге 10 минут это `17:50`
6. Просроченные записи (простой сервиса, закрытое окно) получают `failed` с причиной в `error`, отдельного статуса нет (решено в спеке). Без проверки просрочки записи после простоя пушились бы ночью (подтверждено)
7. Утренний час из спеки заменён планированием при опросе (прежнее допущение, не менялось)
8. Часовой пояс окна это пояс сервера
9. Правки расписания через `PUT` действуют со следующего дня, `active` сразу
10. Остановка: текущий пуш доделывается без отмены, ограничения по времени ожидания нет. Если платформа убьёт процесс по своему таймауту, запись останется `planned` и пуш повторится после старта

## Проверка

Сборка: `go build ./...`, `go vet ./...`, `go test ./...`, `go generate ./...` без ошибок, в схеме `db.Task` в `docs/swagger.json` появились поля `done_commits`, `failed_commits` и `last_run_at`

Табличные тесты `core/schedule_test.go` на чистых функциях с фиксированным `now`:
- `slots`: `now` до окна даёт все точки от `start` до `end` без `end` (при `09:00-18:00` и шаге 10 минут их 54), `now` внутри окна даёт точки от `now.Truncate(step)`, `now` после окна пусто, день вне `days` пусто, `start` не на сетке (`09:05`) даёт первый слот `09:10`, окно короче шага даёт не больше одного слота
- `pick`: `n` не больше числа слотов даёт ровно `n` разных отсортированных слотов из списка, `n` больше числа слотов даёт все слоты, на тысяче повторов повторов внутри результата нет
- `overdueReason`: запись со вчерашней датой просрочена, запись сегодняшняя до `end_time` нет, после `end_time` да
- Тест на `Clock.At` в `task_test.go`: нормальное время, `9:00`, битое значение
- Тест на `Task.FillStats` в `task_test.go`: без записей нули и `null`, смесь `done`, `failed` и `planned` даёт верные счётчики, `last_run_at` берёт максимум `executed_at` и пропускает пустые

Сценарий на живой базе с `CORE_TICK_INTERVAL=1m`, Postgres в WSL как в плане 002 (сетка в минуту, чтобы не ждать десять минут):
1. Старт: таблица `planned_commits` создана, ровно один внешний ключ с каскадом (`DELETE /tasks/{id}` убирает записи таски) и уникальный индекс на месте (`wsl -e docker exec footprints-pg psql ...`), у существующих активных тасок, которым сегодня положено, появились записи только на слоты не раньше текущего
2. Заглушка: таска с окном, покрывающим ближайшие 10 минут, `commits_per_day = 3`. Три записи на разные круглые минуты, в логе три записи заглушки в эти минуты (с точностью до секунд после начала минуты), статусы `done` с `executed_at`, повторных записей заглушки нет. В `GET /tasks` до первого запуска у таски `done_commits` 0, `failed_commits` 0, `last_run_at` равен `null`, после трёх запусков `done_commits` 3, `failed_commits` 0, `last_run_at` совпадает с `executed_at` последней записи
3. Новая таска посреди работы: создана через `POST` при работающем сервере, на следующем опросе получает записи на остаток окна, на слоты не раньше текущего
4. Не её день и закрытое окно: таска с `days` без сегодняшнего дня и таска с окном в прошлом не получают записей, заглушка для них не вызывается
5. Выключение: `PUT {"active": false}` во время работы останавливает выполнение оставшихся записей таски, записи остаются `planned`
6. Рестарт в тот же день: число записей на сегодня не удваивается, `done` не выполняются повторно, оставшиеся `planned` выполняются в своё время
7. Просроченные: у одной записи вручную ставим `planned_at` на вчера, у другой таски сдвигаем `end_time` через `PUT` так, чтобы окно закрылось раньше её слота. На ближайшем опросе обе записи становятся `failed` с причиной в `error` и пустым `executed_at`, заглушка не вызывается, `failed_commits` у этих тасок вырос, `last_run_at` не изменился
8. Ошибка пуша: заглушка подменяется на возврат ошибки через `go build -overlay` (файл в репозитории не правится), запись получает `failed` с текстом в `error`, в логе уровень error, на следующих опросах повтора нет, остальные записи таски не затронуты. `GET /tasks` и `GET /tasks/{id}` показывают `failed_commits` равным числу записей `failed`, `done_commits` прежним, `last_run_at` равным времени неудачной попытки. Ответ `PUT` по этой таске содержит те же значения, у других тасок счётчики свои.
9. Остановка: сервис получает сигнал прерывания, в логе видно завершение ядра и сервера, процесс выходит с кодом 0 сразу, не дожидаясь следующей точки сетки. На Windows сигнал отправляю из отдельной консоли (запуск с новой группой процессов и `CTRL_BREAK`), если не получится, попрошу нажать Ctrl+C в окне с сервером

10. Users после переписывания: `GET /users` и `GET /users/{id}` дают те же значения, что считает `psql` (`select user_id, count(*) from tasks group by user_id`), у пользователя без тасок `tasks_count` равен 0, у несуществующего id ответ 404, после `DELETE` таски счётчик уменьшается, порядок в списке по `id`

Тестовые таски и записи после прогона остаются в базе
